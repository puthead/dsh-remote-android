# DSH Remote 中继部署手册（v2）

> 本手册对应 **协议契约 v2**（`docs/01-设计/协议契约-v2.md`）与 `tools/dsh-relay`（relay 2.0.0）。
> 中继的作用：让**手机在任意网络**下通过自建中继到达家里 PC，而 **PC 不开任何入站端口、手机不直连 PC**。
> 公网形态已于 **2026-10-13** 在真实 VPS 上实测通过：**无域名 → Let's Encrypt IP 地址证书 +
> `wss://<公网 IP>:80`**（手机只认系统信任链，故必须用正式证书；详见 §4.1.1 与 §9.2 实测记录）。
> 本机/内网等价拓扑见 §9.1；其余未实测项仍按 `> 待验证：<具体内容>` 逐条标注。

---

## 1. 部署形态总览

| 形态 | 适用场景 | 中继运行位置 | 手机连的地址 | 状态 |
|---|---|---|---|---|
| A. 本机验证 | 开发/自测/等价拓扑验收 | 与网关同一台 PC | `ws://127.0.0.1:9443`（同机）/ `ws://10.0.2.2:9443`（Android 模拟器） | **已实测** |
| B. 内网服务器 | 家里 NAS/软路由常开 | 局域网内另一台机器 | `ws://<局域网 IP>:9443` | 已具备脚本，未实测 |
| C. 公网 VPS + 证书 | 真正"任意网络" | 公网 VPS（systemd；非 root 绑 <1024 端口需 `AmbientCapabilities=CAP_NET_BIND_SERVICE`） | 有域名：`wss://relay.example.com`；**无域名：`wss://<公网 IP>:80`（Let's Encrypt IP 地址证书）** | **已实测**（2026-10-13，IP 证书形态，见 §9.2） |
| D. Windows 服务 | 只有 Windows 机器常开 | Windows Server/PC | `ws://<IP>:9443` 或 `wss://` | 已给命令，未实测 |

一键脚本（全部在仓库根执行）：

```
powershell -File scripts/setup-relay.ps1   -Home ".runtime\relay-home" -Port 9443 -TlsMode off
powershell -File scripts/start-relay.ps1   -Home ".runtime\relay-home"          # 分离启动 + PID 文件 + /health 等待
powershell -File scripts/relay-pair.ps1                                         # 生成配对码 + 中继隧道地址 + 二维码
powershell -File scripts/stop-relay.ps1    -Home ".runtime\relay-home"          # 幂等停止
powershell -File scripts/deploy-relay.ps1  -Host relay.example.com -User ops -KeyFile <key> -PublicUrl relay.example.com -DryRun
```

## 2. 三方地址：各用哪个（**本轮最容易踩的坑**）

中继把 `tunnelUrl` 交给手机，地址**派生自配置里的 `publicUrl`（未设置时回退 `relayName`）**。
若 `relayName` 是手机解析不了的域名/别名，**手机永远显示离线，而 PC 侧一切正常**，极难排查
（真机实测报错原文：`Unable to resolve host "relay.e2e.local": No address associated with hostname`）。

| 谁 | 连谁 | 用什么地址 |
|---|---|---|
| 网关（PC） | 中继 | `ws://127.0.0.1:<port>`（同机）或 `wss://<域名>`（VPS） |
| 手机 | 中继 | **`publicUrl` 声明的那一个**：公网域名 / 局域网 IP / 模拟器 `10.0.2.2` |
| 手机 | 网关 | **不直连** —— 这正是本轮架构的核心（判据 A 证明它连不上） |

因此**中继配置必须显式写 `publicUrl`**（必须是 `ws://` / `wss://` / `http://` / `https://` 开头）：

```json
{
  "relayName": "relay.example.com",
  "publicUrl": "wss://relay.example.com"
}
```

| 场景 | `publicUrl` 写法 |
|---|---|
| 公网 VPS + 域名 + 正式证书 | `wss://relay.example.com` |
| **公网 VPS + 无域名**（已实测） | `wss://<公网 IP>:80` —— Let's Encrypt **IP 地址证书**（6 天有效期 + 续期钩子，见 §5.1） |
| 公网 VPS + 自签证书 | ❌ **release APK 连不上**：App **没有**"信任自签证书"开关，只认系统信任链（需求 FR-15 / O8）。自签仅用于本机/内网与 PC 侧联调 |
| 本机验证（手机与 PC 同机/同网） | `ws://127.0.0.1:9443` |
| Android 模拟器（模拟器内的宿主机回环） | `ws://10.0.2.2:9443` |
| 局域网内另一台中继机 | `ws://192.168.x.y:9443` |

## 3. 本机 / 内网验证（形态 A、B）

### 3.1 初始化 + 启动

```powershell
# 1) 生成配置（默认 host=0.0.0.0、port=9443、tls.mode=off；relaySecret 自动随机）
powershell -File scripts/setup-relay.ps1 -Home ".runtime\relay-home" -Port 9443 -TlsMode off -PublicUrl "ws://127.0.0.1:9443"

# 2) 启动（stdout 只有一行 JSON，日志走 stderr；脚本据此拿真实端口并写 relay.pid.json）
powershell -File scripts/start-relay.ps1 -Home ".runtime\relay-home"

# 3) 验证
curl.exe http://127.0.0.1:9443/health
```

期望输出（实测）：

```json
{"ok":true,"relayVersion":"2.0.0","apiVersion":2,"uptimeMs":605,"homes":0,"devices":0,"relayName":"relay.local"}
```

### 3.2 让网关连上中继

网关侧配置（`<网关运行目录>\config.json`）：

```json
"relay": {
  "enabled": true,
  "url": "ws://127.0.0.1:9443",
  "homeName": "我的台式机",
  "relaySecret": "<与中继 config.json 的 relaySecret 相同；中继未设则为空>"
}
```

然后在 PC 本机（**只接受回环来源**）触发连接：

```powershell
curl.exe -X POST http://127.0.0.1:8787/api/v2/relay/connect
curl.exe http://127.0.0.1:8787/api/v2/relay/status
```

`relay/status` 期望 `"connected": true`、`"lastError": null`。注册信息由网关自动持久化到
`<网关运行目录>\relay.json`（含 `homeId`/`homeToken`，**这是秘密，不要提交**）。

### 3.3 配对手机

```powershell
powershell -File scripts/relay-pair.ps1     # 打印 6 位码 + 中继隧道地址 + 文本二维码
```

手机端：设置页填**中继地址**（= §2 的 `publicUrl`）+ 6 位配对码 → 中继把 claim 转发给 PC 网关 → 手机拿到设备令牌。

## 4. 公网部署（形态 C：VPS / 云服务器 ECS / 轻量应用服务器）

> **VPS 与 ECS 是同一类东西**（阿里云 ECS、腾讯云 CVM/轻量、华为云 ECS、AWS EC2…都算）。
> 本节的"VPS"泛指任何**有公网 IP、能跑 Node、能被手机和 PC 连到**的 Linux 机器，不要求特定厂商。
> 中继侧**零第三方依赖**（只用 Node 内置模块，无 `package.json`/无需 `npm install`），
> 对机器要求极低：**1 核 512 MB、Node 18+ 即可**，磁盘占用只有几十 MB。

> **已实测（2026-10-13）**：本节命令链在腾讯云 CVM（Ubuntu 26.04 + Node 22.22.1 + Let's Encrypt IP
> 地址证书 + 端口 80）上真实执行通过：打包上传 → `init` → systemd 常驻 → 公网严格 TLS 校验 →
> 手机侧经公网配对与真实任务往返（证据目录见 §9.2）。
> `-DryRun` 只打印命令、不联网；真实执行前请核对 §4.1 的放行端口与 Node 版本。

### 4.1 前置

1. **放行端口（ECS 上叫「安全组」，最容易漏的一步）**：入方向放行 `TCP 22`（SSH）与中继端口。
   - **有域名**：中继用 `TCP 9443`（或任意高端口）即可；80/443 由 certbot 续期时临时占用。
   - **无域名 + IP 地址证书（已实测形态）**：中继直接监听 `TCP 80`（手机连 `wss://<公网 IP>:80`）；
     **80 同时是 certbot http-01 续期入口**，续期期间用 `pre_hook` 停中继、`post_hook` 拉起（见 §5.1）。
   - 只开了系统防火墙但没配安全组，会表现为"远端 `curl 127.0.0.1:<port>/health` 正常、手机却连不上"。
   - 若用 `ufw`/`firewalld`：`sudo ufw allow 22/tcp; sudo ufw allow 80/tcp`（本机镜像里 ufw 默认 inactive，但别漏）。
2. **安装 Node.js 18+**（`node --version`）：ECS 镜像通常自带旧版或不带。
   ```bash
   curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash - && sudo apt install -y nodejs   # Debian/Ubuntu
   # 或：sudo dnf module install nodejs:20                                             # RHEL 系
   ```
   **实测捷径**：Ubuntu 26.04 的 universe 源里已有 `nodejs 22.22.1`，直接 `sudo apt-get install -y nodejs`
   即可（中继零第三方依赖，**不需要 npm**）。
   `deploy-relay.ps1` 默认按 PATH 上的 `node` 调用；装在别处用 `-RemoteNode /usr/local/bin/node` 指定。
3. **本地有 `ssh`/`scp`**（Windows 10+ 自带 OpenSSH 客户端即可，本机已实测存在）。
4. **决定 TLS 形态**（见下表）：有域名 → 正式证书；**无域名 → Let's Encrypt IP 地址证书（已实测，推荐）**；
   实在拿不到证书才临时用 `off`（明文，且 release APK 连不上，只够 debug 变体验证链路）。

### 4.1.1 有域名 / 无域名，两种配法（**决定手机该连哪个地址**）

| 场景 | `-TlsMode` | `-RelayName` | `-PublicUrl`（手机侧看到的中继地址） |
|---|---|---|---|
| **有域名 + 正式证书**（推荐） | `file`（配 `-TlsCertFile`/`-TlsKeyFile`） | `relay.example.com` | `wss://relay.example.com` |
| **无域名 + IP 地址证书**（**2026-10-13 已实测**） | `file` + `-LetsEncryptCertName <公网 IP>` | `<公网 IP>` | `wss://<公网 IP>:80` |
| 无域名 + 明文（只用来先打通链路） | `off` | `<ECS 公网 IP>` | `ws://<ECS 公网 IP>:9443`（**release APK 连不上**，明文只有 debug 变体放开） |
| 有域名 + 自签（仅联调） | `selfsigned` | `relay.example.com` | ❌ release APK 连不上（App 无自签信任开关）；仅供本机/内网或 debug 变体 |

> **`-PublicUrl` 必须是手机真正能连到的地址**，这是"手机连不上"的头号原因：
> 中继把它作为 `tunnelUrl` 交给手机（`relay` 块里的字段）。若不传，中继会**按 `-RelayName` 派生** ——
> 于是「relayName 是内网别名 / 是 IP 而证书 CN 是域名」这类组合会让手机永远连不上。
> **无域名 + `off` 时没有 TLS**：隧道内容在公网上是明文，**且 release APK 本身就拒绝明文**
> （`cleartextTrafficPermitted="false"`），只能拿 debug 变体验证链路，**不要长期用**。
> 无域名又必须加密：用 **Let's Encrypt IP 地址证书**（`-LetsEncryptCertName`，见 §5.1）。
> **不要**指望"手机端信任自签证书开关"——那个开关在 App 里根本不存在（需求 FR-15 / O8）。

### 4.2 一键部署（DryRun 先看命令）

**有域名 + 正式证书（推荐）**：

```powershell
powershell -File scripts/deploy-relay.ps1 `
  -Host relay.example.com -User root -KeyFile "$env:USERPROFILE\.ssh\id_ed25519" `
  -RemoteDir /opt/dsh-relay -RemotePort 9443 `
  -RelayName relay.example.com -PublicUrl wss://relay.example.com `
  -TlsMode file -TlsCertFile /etc/letsencrypt/live/relay.example.com/fullchain.pem `
  -TlsKeyFile /etc/letsencrypt/live/relay.example.com/privkey.pem -DryRun
```

**无域名 + IP 地址证书（2026-10-13 实测形态）**：先在服务器上签一张 6 天有效的 IP 证书
（certbot **必须 ≥ 5.4**，apt 里的 4.0.0 不支持 IP 证书，用 snap 版）：

```bash
# 一次性；80 端口必须对 Let's Encrypt 可达（http-01）
sudo snap install certbot --classic
sudo /snap/bin/certbot certonly --preferred-profile shortlived --standalone \
  --ip-address 47.98.12.34 --cert-name 47.98.12.34 \
  --non-interactive --agree-tos --register-unsafely-without-email
```

```powershell
# -LetsEncryptCertName 会：把 fullchain/privkey 同步进运行目录 + 安装并写入续期钩子（见 §5.1）
powershell -File scripts/deploy-relay.ps1 `
  -Host 47.98.12.34 -User ubuntu -KeyFile "$env:USERPROFILE\.ssh\id_ed25519" `
  -RemoteDir /opt/dsh-relay -RemotePort 80 -TlsMode file `
  -LetsEncryptCertName 47.98.12.34 -RelayName 47.98.12.34 -PublicUrl wss://47.98.12.34:80 -DryRun
```

**无域名 + 明文（只够 debug 变体验证链路）**：

```powershell
powershell -File scripts/deploy-relay.ps1 `
  -Host 47.98.12.34 -User root -KeyFile "$env:USERPROFILE\.ssh\id_ed25519" `
  -RemoteDir /opt/dsh-relay -RemotePort 9443 `
  -RelayName 47.98.12.34 -PublicUrl ws://47.98.12.34:9443 -TlsMode off -DryRun
```

> `-PublicUrl` 会被透传给远端 `init --public-url`（已修：早期版本只改了本地暂存配置，
> 远端 `init --force` 会重新生成配置，导致该参数被静默丢弃 → 手机拿到按 `relayName` 派生的错误地址）。

去掉 `-DryRun` 即真实执行，脚本按顺序做：

| 步骤 | 命令（实测打印） |
|---|---|
| 打包 | `tar.exe -czf <staging>\dsh-relay-<stamp>.tgz -C <staging>\pack dsh-relay` —— 脚本先把 `tools/dsh-relay` 复制到 `<staging>\pack` 并删掉 `test/`、`node_modules`。**不再用 `--exclude`**：Windows 自带 `tar.exe` 加 `--exclude` 会报 `tar.exe: : Couldn't visit directory: No such file or directory` |
| 上传 | `scp -P 22 -i <key> <tgz>…`（unit 文件同理；用 `-LetsEncryptCertName` 时还会上传证书部署钩子与续期钩子脚本） |
| 初始化 | `ssh … "bash -lc 'set -e; sudo install -d -m 0755 /opt/dsh-relay /opt/dsh-relay/logs /opt/dsh-relay/tls; (id -u dsh-relay >/dev/null 2>&1 \|\| sudo useradd --system --home-dir /opt/dsh-relay --shell /usr/sbin/nologin dsh-relay); sudo tar -xzf … --strip-components=1; sudo install -m 0644 -o dsh-relay -g dsh-relay /etc/letsencrypt/live/<IP>/fullchain.pem /opt/dsh-relay/tls/relay.crt; sudo install -m 0600 -o dsh-relay -g dsh-relay /etc/letsencrypt/live/<IP>/privkey.pem /opt/dsh-relay/tls/relay.key; sudo install -m 0755 /tmp/dsh-relay-cert-deploy.sh /usr/local/bin/dsh-relay-cert-deploy; sudo bash /tmp/dsh-relay-renew-hooks.sh <IP>; node /opt/dsh-relay/relay.mjs init --home /opt/dsh-relay --force --port 9443 --host 0.0.0.0 --relay-name <IP> --tls-mode file --public-url wss://<IP>:9443 --cert /opt/dsh-relay/tls/relay.crt --key /opt/dsh-relay/tls/relay.key --relay-secret ***; sudo chown -R dsh-relay:dsh-relay /opt/dsh-relay; sudo install -m 0644 /tmp/dsh-relay.service /etc/systemd/system/; sudo systemctl daemon-reload; sudo systemctl enable --now dsh-relay; sleep 2; sudo systemctl is-active dsh-relay; curl -skS https://127.0.0.1:9443/health'"` |
| 公网校验 | `GET https://47.98.12.34:9443/health` —— **URL 由 `-PublicUrl` 归一化**（早期版本会把 `wss://…` 直接拼成 `https://wss://…/health` 永远失败，缺端口还会落到 443 挂上百秒）。只有自签形态才需要 `-Insecure`；**该端口必须已在云安全组放行**（本项目现网是 9443） |

> **回环 curl 一定失败是正常的**：IP 证书的 SAN 只有公网 IP，`curl https://127.0.0.1:<port>/health`
> 会报 `no alternative certificate subject name matches target ipv4 address '127.0.0.1'`。
> 本机自检请用**公网 IP**（严格校验，能顺便证明证书链正确）或显式 `-k`；脚本内部那条回环检查带 `-k`。

systemd unit（脚本生成，最小权限）：

```ini
[Service]
Type=simple
User=dsh-relay
WorkingDirectory=/opt/dsh-relay
ExecStart=node /opt/dsh-relay/relay.mjs serve --home /opt/dsh-relay
Restart=always
RestartSec=3
# 停服上限：中继进程内另有 8 秒看门狗（DSH_RELAY_SHUTDOWN_GRACE_MS，默认 8000），
# 这里给 systemd 一个更宽的兜底，避免现场那种「stop-sigterm 卡满 90 秒被 SIGKILL」（见 §9.4）。
TimeoutStopSec=15
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/dsh-relay
# 非 root 服务要监听 <1024 端口（例如直接把中继挂在 80）必须显式授予绑定能力；
# 端口 >=1024 时这两行是无害的空操作。
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
```

### 4.3 手工部署（脚本不可用时）

```bash
# 本机（GNU tar 支持 --exclude；Windows 自带 tar.exe 会报错，见 §4.2 的打包说明）
tar -czf dsh-relay.tgz -C tools dsh-relay --exclude=dsh-relay/test --exclude=dsh-relay/node_modules
scp dsh-relay.tgz ops@<host>:/tmp/
# VPS
sudo mkdir -p /opt/dsh-relay && sudo chown "$USER" /opt/dsh-relay
tar -xzf /tmp/dsh-relay.tgz -C /opt/dsh-relay --strip-components=1
# ① 自签形态（仅本机/内网联调；release APK 连不上，见 §2）
node /opt/dsh-relay/relay.mjs init --home /opt/dsh-relay --force --port 9443 --host 0.0.0.0 \
     --relay-name relay.example.com --tls-mode selfsigned --relay-secret "$(openssl rand -base64 24 | tr '+/' '-_' | tr -d '=')"
# ② 正式证书 / IP 地址证书形态：**必须显式给 --cert/--key**
#    （旧版 CLI 在 init 分支丢这两个参数，报「配置错误：tls.mode=file 时必须同时提供
#      tls.certFile 与 tls.keyFile」——这是真缺陷，本仓库已修 + 有回归测试）
node /opt/dsh-relay/relay.mjs init --home /opt/dsh-relay --force --port 9443 --host 0.0.0.0 \
     --relay-name 47.98.12.34 --tls-mode file --cert /opt/dsh-relay/tls/relay.crt \
     --key /opt/dsh-relay/tls/relay.key --public-url wss://47.98.12.34:9443 \
     --relay-secret "$(openssl rand -base64 24 | tr '+/' '-_' | tr -d '=')"
node /opt/dsh-relay/relay.mjs serve --home /opt/dsh-relay   # 前台先试跑
sudo systemctl enable --now dsh-relay
curl -sk https://127.0.0.1:<port>/health    # IP 证书 SAN 只有公网 IP → 回环校验必然失败，只能 -k
```

> ⚠️ **`init` 会重写 `config.json` 与 `homes.json`**：只是「更新代码重新部署」时**不要跑 `init`**，
> 否则已注册的 home 会被清空（网关会自动重新注册，但期间手机会短暂离线）。
> 手工写 systemd unit 时记得带上 §4.2 里的 `AmbientCapabilities` —— 否则非 root 服务绑 80 会以
> `EACCES` 退出（表现为 `systemctl status` 里反复 `Restart`）。

Windows 形态（`-Target Windows`）：脚本打印 `schtasks /Create /TN dsh-relay /SC ONSTART /RU SYSTEM …`
+ `schtasks /Run /TN dsh-relay`，并用 `Invoke-WebRequest http://127.0.0.1:9443/health` 校验。

## 5. TLS 证书

| 模式 | 用途 | 说明 |
|---|---|---|
| `off` | 本机/内网验证 | 明文 `ws://`；Android **仅 debug 变体**放开明文，release 直接拒绝 |
| `selfsigned` | 本机/内网联调 | 首次 `init`/`serve` 在 `<home>/tls/` 生成 `relay.crt`/`relay.key`（默认 825 天）。**手机端连不上**：App 不提供自签信任开关（需求 FR-15 / O8），release 只认系统信任链 |
| `file` | 生产（含无域名的 IP 证书） | `tls.certFile`/`tls.keyFile` 指向证书（PEM 链 + 私钥）；无域名时用 IP 地址证书，见 §5.1 |

- 证书续期后**重启中继**即可生效（`systemctl restart dsh-relay`）；`file` 模式建议用续期钩子自动做（§5.1）。
- 证书里的身份必须等于手机实际连接的地址（`publicUrl` 的 host）：域名证书绑域名；**IP 证书的 SAN 里必须是那个公网 IP**。
  LE 的 IP 证书 **`subject` 是空的**（身份全在 SAN，`X509v3 Subject Alternative Name: critical`），这是合法证书 ——
  中继 2.0.0 已适配（早期版本会在启动日志里对空 subject 调 `.replace()` 直接崩溃，见 §10 排障表）。
- 自签 / IP 证书下 `curl` 回环校验需 `-k`；`Invoke-DshApi -Insecure` 仅供本机验证，生产禁用。

### 5.1 无域名：Let's Encrypt IP 地址证书（6 天有效期 + 续期钩子，2026-10-13 实测）

Let's Encrypt 自 2026-01 起支持 **IP 地址证书**（GA），自 2026-03 起 certbot ≥ 5.4 支持签发；
IP 证书**只能用 `shortlived` profile**，有效期 **6 天**，续期靠 **http-01（80）/ tls-alpn-01（443）**：

```bash
# 服务器（一次性）。Ubuntu 26.04 的 apt 版 certbot 是 4.0.0（不支持 IP 证书）→ 用 snap 版
sudo snap install certbot --classic                     # 实测装到 5.8.0
sudo /snap/bin/certbot certonly --preferred-profile shortlived --standalone \
  --ip-address 47.98.12.34 --cert-name 47.98.12.34 \
  --non-interactive --agree-tos --register-unsafely-without-email
# 产物：/etc/letsencrypt/live/47.98.12.34/{fullchain.pem,privkey.pem}（ECDSA，链 4 张，issuer ... CN=YE2）
```

**续期钩子必须写进 renewal conf**（关键坑）：直接 `certbot renew --pre-hook … --deploy-hook … --post-hook …`
在"证书还没到期、`No renewals were attempted`"时**不会把钩子持久化**（实测 conf 里不留钩子行）。
`deploy-relay.ps1 -LetsEncryptCertName` 会生成两个脚本并把下面三行插进
`/etc/letsencrypt/renewal/<IP>.conf` 的 `[renewalparams]` 段（幂等，先备份）：

```ini
pre_hook = systemctl stop dsh-relay
renew_hook = /usr/local/bin/dsh-relay-cert-deploy
post_hook = systemctl start dsh-relay
```

`dsh-relay-cert-deploy` 做的事：把新 `fullchain.pem`/`privkey.pem` `install` 成
`/opt/dsh-relay/tls/relay.{crt,key}`（属主 `dsh-relay`、私钥 600）→ `systemctl restart dsh-relay` → `logger -t dsh-relay-cert` 记账。
它**带测试证书护栏**：`openssl x509 -issuer` 命中 `*STAGING*|*Fake*|*Pretend*` 就跳过部署并 `exit 0`
（否则有人跑一次 `certbot renew --dry-run` 就会把 staging 证书铺到生产，**手机侧全部连不上**）。

验证与两个坑：

```bash
sudo certbot renew --cert-name 47.98.12.34 --dry-run --no-random-sleep-on-renew   # 期望 all simulated renewals succeeded
sudo journalctl -t dsh-relay-cert -n 20        # 看部署钩子是否真的跑过
```

- `certbot renew` 在非交互模式下会**随机睡 ≤480 s 再动手**（`Non-interactive renewal: random delay of 410.18… seconds`），
  看起来像卡死；手工验证时加 `--no-random-sleep-on-renew`，real 续期不用管（`snap.certbot.renew.timer` 每天两次 + ARI 驱动）。
- **续期期间中继会短暂下线**（standalone 需要独占 80）：实测网关自动重连（`relay/status` 的 `reconnects` +1、`lastError` 仍为 `null`），
  手机侧重连即可，无需人工干预。若不想有这段窗口，就让中继换到 9443 等高端口，把 80 只留给 certbot（`pre_hook/post_hook` 可去掉）。
- **证书 6 天寿命 ⇒ 续期即生命线**：部署完务必核对 `systemctl list-timers snap.certbot.renew.timer` 与
  `certbot certificates` 的到期时间，并至少跑通一次 `--dry-run`。

### 7.1 网关"中途死掉"也要能自愈（`watchdog-gateway.ps1`）

**为什么需要**：2026-10-13 22:21:49 实测到网关进程意外结束（`logs/gateway-console-*.err.log` 末尾出现 `^C`），
之后 `/api/v1/health` 无响应、中继侧 `homes:0`，**手机拿到 503 `home_offline`，直到人回家手动重启才恢复**。
开机自启只解决"重启电脑"，解决不了"进程中途没了"。

| 动作 | 命令 |
|---|---|
| 只体检一次（给计划任务用） | `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\watchdog-gateway.ps1 -Once` |
| 常驻体检（循环，默认 60 秒一次） | `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\watchdog-gateway.ps1 -IntervalSeconds 120 -Quiet` |
| 停止常驻看门狗（不动网关本体） | `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\watchdog-gateway.ps1 -Stop` |

判定与动作：①`GET /api/v1/health` 不可达 → 判"网关没了"→ 调 `start-gateway.ps1` 拉起并复验 30 秒；
②网关活着但 `/api/v2/relay/status.connected=false` 持续超过 `-RelayGraceSeconds`（默认 180 秒）→ 判"隧道卡死"→ 同样重启；
③一小时内重启次数超过 `-MaxRestartsPerHour`（默认 12）→ 停手退避，避免"起不来就一直重启"的风暴；
④**单例**：循环模式启动时若 `logs\watchdog.pid` 指向的进程还活着（且命令行里确实是本脚本），本次直接退出，不会双份体检。
日志 `logs\watchdog.log`、限流状态 `logs\watchdog-state.json`、自身 PID `logs\watchdog.pid`（`-Once` 不写 PID 文件）。

自启两条路线（`install-autostart.ps1`）：

| 路线 | 命令 | 权限 | 说明 |
|---|---|---|---|
| 计划任务 | `install-autostart.ps1 -WithWatchdog` | **需要管理员** | 除登录自启任务外，再注册 `DshRemoteGatewayWatchdog`（默认每 2 分钟跑一次 `-Once -Quiet`）；非提权会话实测直接 `Access is denied` |
| Startup 文件夹 | `install-autostart.ps1 -StartupFolder` | **不需要管理员** | 在 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\DshRemoteGateway.cmd` 写一个 ASCII 启动器，登录时 `start /min` 同时拉起网关 + 看门狗 |

卸载：`uninstall-autostart.ps1`（顺带删看门狗任务与 Startup 启动器、停常驻看门狗；加 `-KeepWatchdog` 可保留看门狗，加 `-StopGateway` 连网关一起停）。

> 桌面启动器 `启动DSH远程.cmd`（多合一控制台，菜单 1「启动服务」）也会在拉起网关后请求一次看门狗（重复启动会被单例判定挡掉），
> 所以"用户自己点启动器"这条路线同样具备进程级自愈。（旧的 `启动远程网关.cmd` 已于 2026-10-16 归档到 `.archive\desktop\`。）

## 8. 首次启动会物化 `profiles/sdk`（**"手机任务"能否用的前提**）

网关自有 `DSH_HOME`（默认 `<网关运行目录>\dsh-home`，可用环境变量 `DSH_HOME` 覆盖）下，

```powershell
curl.exe http://127.0.0.1:8787/api/v2/relay/status          # connected=true
curl.exe -X POST http://127.0.0.1:8787/api/v2/tasks `
  -H "Authorization: Bearer <deviceToken>" -H "Content-Type: application/json" `
```

完全离线且物化失败时：把网关自有 `DSH_HOME` 指向一个**已经物化过 `profiles/sdk` 的 home**（例如已有的
`.dsh` 副本），或用 `-DshHome`/`DSH_HOME` 显式指定；**不要把镜像源（真实 `%USERPROFILE%\.dsh`）当写目标**。

### 9.4 停服卡 90 秒 → 已修（中继 v2.0.1）

**现场（22:12:15）**：`systemctl stop/restart dsh-relay` 时服务进入 `stop-sigterm`，**卡满 90 秒**被
`State 'stop-sigterm' timed out. Killing.` + `SIGKILL`（`Failed with result 'timeout'`，重启期间手机全部不可用）。
中继自己的日志却显示关闭已开始：`14:12:15.106Z 收到 SIGTERM，开始优雅关闭` → `.107Z home 隧道下线(peer_closed)`
→ `.121Z socket 关闭 code=1001` → **之后 90 秒零日志**，直到新进程 `TLS 证书已加载`。
→ 卡点在 `relay.close()` 内部：**`server.close()` 的回调在「Linux + Node 22 + TLS 隧道」现场可能永不返回**，
而当时 `close()` 里 `await closed` 没有任何上限。

**修复（三处一起）**：
1. `lib/http.mjs`：`close()` 里等 `server.close` 回调改为**有界**——3 秒未返回就强制销毁剩余连接
   （`CLOSE_CONNECTION_GRACE_MS=3000`），再给 1 秒（`CLOSE_FORCE_GRACE_MS=1000`），仍不返回就打印 warn 继续关闭流程。
2. `relay.mjs`：`shutdown()` 加**进程内看门狗**（`DSH_RELAY_SHUTDOWN_GRACE_MS`，默认 8000ms）——超时打印
   `优雅关闭超过 Nms 仍未完成，强制退出（残留句柄：…）`（用 `process.getActiveResourcesInfo()` 留证据）并 `exit(1)`；
   同时加 `stopping` 防重入。
3. systemd unit：加 `TimeoutStopSec=15`（比进程内 8 秒更宽，作为兜底）。

**回归测试**：新增 `tools/dsh-relay/test/shutdown.test.mjs` 三条——双隧道在线时 `close()` < 3 秒、
`close()` 后端口立刻可重新绑定、**把 `server.close` 换成永不回调也必须在上限内返回**（实测 4058ms）。
中继全套 **99/99 通过**。

**服务器复验（22:20:42，网关 home 隧道在线时执行真实重启）**：`systemctl restart dsh-relay` 耗时
**0.049277030 秒**；journal `Stopping … Deactivated successfully … Started`（**无 timeout、无 SIGKILL**）；
中继日志 `14:20:42.489Z 收到 SIGTERM` → `.790Z 新进程 TLS 证书已加载`（≈300ms 完成关闭），无强制销毁告警。

## 10. 排障表

| 现象 | 首要排查 | 处置 |
|---|---|---|
| **手机一直"连接中断/无法解析主机"（⚠️ 最常见，先看这条）** | **`publicUrl` 是否是手机可达地址**；手机能否解析该域名（`adb shell ping <域名>`） | 按 §2 表格改 `publicUrl`；模拟器用 `ws://10.0.2.2:<port>` |
| 网关连不上中继 | `<网关运行目录>\logs\gateway-console-*.err.log` 与 `GET /api/v2/relay/status` 的 `lastError` | 检查 `relay.url`、端口、`relaySecret`；确认中继 `/health` 正常 |
| `GET /api/v2/relay/status` 里 `reconnects` 持续增长，或中继日志每 ~30s 出现 `心跳超时（Nms 无任何入站活动…）` / `home 隧道下线（reason=timeout）` | `heartbeat.timeoutMs` 是否被配成与 `intervalMs` 相近 | **中继现在启动即拒**：`timeoutMs < intervalMs×2` 会以退出码 2 报错并提示改法（1:1 会让健康连接在第一个心跳周期就被误杀且不可自愈）。推荐 `intervalMs: 30000 / timeoutMs: 90000`（=3×），或删掉整个 `heartbeat` 字段用默认值；也可 `node relay.mjs init --home <运行目录> --force` 重新生成。`scripts/setup-relay.ps1` 会自动把旧配置修复为 ×3 |
| 升级后中继起不来、报「配置错误：heartbeat.timeoutMs…必须 ≥ intervalMs×2」 | 旧配置是从**旧默认值**（30000/30000）生成的 | 同上：`setup-relay.ps1` 自动修复，或手工改成 90000 / 删字段 |
| 手机任务提交后立刻失败 / `POST /api/v2/tasks` 5xx | 网关自有 `DSH_HOME` 下 `profiles/sdk` 是否物化成功（§8） | 看 `logs\gateway-console-*.err.log`；必要时换一个已物化的 home |
| 配对码换了令牌仍 401 | 设备令牌轮换后旧连接未失效（契约 §2.3） | 重启中继或等 ≤5s 热加载对账；手机重新配对 |
| `Sec-WebSocket-Accept 不匹配` | 中继 `WS_GUID` 是否为 RFC 6455 正确值 | `node scripts/tests/relay-rfc-check.mjs`（用官方向量，红线级回归） |
| `pair/claim` 返回 503 `home_offline` | 网关隧道是否在线、PC 是否睡眠 | 检查 `relay/status.connected`；确认 PC 未休眠、网关进程存活 |
| **手机报证书错误、连不上，而 PC 侧 `relay/status` 一切正常** | 中继用的是**自签**证书？ | App **没有**"信任自签证书"开关（FR-15 / O8），release 只认系统信任链 → 换正式证书（无域名用 §5.1 的 IP 地址证书）；自签/明文只能配 debug 变体 |
| 中继启动即崩：`TypeError: Cannot read properties of undefined (reading 'replace')`（`lib/tls.mjs`） | 证书的 `subject` 为空 —— **LE IP 证书就是这种形态**（身份全在 SAN） | 升级到仓库当前版本（已加 `describeCertificateSubject`：空 subject 退化为打印 SAN 摘要） |
| `配置错误：tls.mode=file 时必须同时提供 tls.certFile 与 tls.keyFile` | 旧版 `relay.mjs init` 分支丢了 `--cert/--key` | 升级后重跑 `init`（已加回归测试），或手工把路径写进 `config.json` 的 `tls.certFile`/`tls.keyFile` |
| 非 root 服务反复 `Restart`、日志 `EACCES`/`bind EACCES 0.0.0.0:80` | unit 缺绑定能力 | 加 `AmbientCapabilities=CAP_NET_BIND_SERVICE` + `CapabilityBoundingSet=CAP_NET_BIND_SERVICE`（§4.2 生成的 unit 已含） |
| `certbot renew` 像卡死；或 `No renewals were attempted` 且钩子没生效 | ①非交互续期会**随机睡 ≤480 s** ②证书未到期时 `--pre-hook/--deploy-hook` 参数**不会持久化** | 手工验证加 `--no-random-sleep-on-renew`；钩子必须写进 `/etc/letsencrypt/renewal/<名>.conf`（§5.1 的脚本会写），用 `journalctl -t dsh-relay-cert` 确认钩子真跑过 |
| 公网 `curl https://<IP>/health` 挂上百秒后 `(28) Failed to connect` | 忘了写端口 → 默认 443，而安全组只放行 22/80/9443 | 显式写端口（现网 `https://<IP>:9443/health`），并核对安全组 |
| `systemctl stop/restart dsh-relay` 卡满 90 秒，journal 出现 `State 'stop-sigterm' timed out. Killing.` + SIGKILL | `close()` 里等 `server.close` 回调无上限（Linux + Node 22 + TLS 隧道的现场回调可能永不返回） | 升级到中继 **v2.0.1**（3s/1s 有界等待 + 进程内 8s 看门狗）并给 unit 加 `TimeoutStopSec=15`；实测重启 **0.049s**，详见 §9.4 |
| 手机报 `503 home_offline`，而中继 `/health` 显示 `homes:0` | **家里网关进程没了**（不是中继问题） | 看 `<网关运行目录>\logs\gateway-console-*.err.log` 末尾与 `logs\gateway-exit-*.log`（退出码：`0` 正常、`1` JS 崩溃、`3221225786`/`-1073741510` = 被 Ctrl+C 结束）；`scripts/start-gateway.ps1` 重新拉起（重复启动检测是幂等的）。**免手动**：常驻 `scripts\watchdog-gateway.ps1`（§7.1），或管理员身份跑 `scripts/install-autostart.ps1 -WithWatchdog`、无管理员跑 `-StartupFolder` |
| 手机报 `503 home_offline`，但网关进程活着 | 隧道没连上（中继在重启/网络抖动） | `curl.exe http://127.0.0.1:8787/api/v2/relay/status` 看 `connected/lastError`；≥180 秒仍断开时看门狗会重启网关（§7.1） |
| 看门狗自己是不是在跑？ | 常驻实例会写 PID 文件 | `Get-Content <网关运行目录>\logs\watchdog.pid`（含 `pid/intervalSeconds`）；`logs\watchdog.log` 每 30 次体检留一条"体检正常"，重启会留 `[warn] 准备重启网关。原因：…` 与 `[ok] 网关已恢复` |
| 端口被占 | `netstat -ano \| findstr :9443` | 结束占用进程或 `-Port` 换端口（客户端/网关同步改） |

## 11. 安全红线（违反即不可上线）

1. **网关 HTTP 只绑 `127.0.0.1`**；`config.host` 写成 `0.0.0.0` 时 v2 relay 功能必须拒绝启动。
2. 中继**只存 `sha256`**（homeToken/deviceToken）；日志中令牌/配对码/Authorization 一律前 4 位 + `****`。
3. 中继**不落盘消息正文**，只有内存连接与流表；`homes.json` 只含摘要与元数据。
4. `pair/open` 与 `relay/*` 管理端点**只接受回环来源**；home 经隧道只能访问契约 §3.4 的三条控制面路由。
5. `relaySecret` 为空只适用于本机回环；**公网必须设置**（`POST /api/v2/homes` 的注册口令）。
6. 手机端**不存在**自签证书信任开关（App 只用系统信任链，需求 FR-15 / O8）；因此公网必须使用**系统信任链可校验的正式证书**（无域名用 §5.1 的 IP 地址证书）。自签证书与明文 `ws://` 仅限本机/内网与 debug 变体联调。
7. 生产用 `wss://` + 正式证书；Android release 变体不得放开明文 HTTP。
