## 0. 为什么是这个形状（设计前提）

1. **PC 不开任何入站端口**。家里 PC 只做**出站长连接**到中继；因此不需要公网 IP、不需要端口映射、不需要改路由器。
2. **手机不直连 PC**。手机在 4G/5G 下只连中继；中继把请求喂给 PC 的隧道。
3. **中继不认识业务**。中继只做「认证 + 多路复用 + 字节转发」，不解析会话内容，不落库消息正文。
4. **令牌仍由 PC 生成**。`deviceToken` 由**网关**生成、只在 PC 侧以 `sha256` 存储；中继只存 `sha256(deviceToken)` 作为隧道准入的第二道闸。中继被拖库也无法冒充设备。
5. **离线可降级**。PC 掉线时中继立刻告知手机 `home_offline`，手机显示"电脑离线"而不是转圈。

### 0.1 拓扑（两处不同网络，仅中继可达）

```
   ┌─────────────── 手机网络（4G/5G / 任意 Wi-Fi）────────────────┐
   │  Android App（深色对话式控制台）                              │
   │   ├─ 电脑会话（镜像；手机可续聊 → 由电脑端 runtime 执行）      │
   │   ├─ 手机任务（可续聊，网关自有 DSH_HOME）                    │
   │   ├─ 工作区（文件/改动/diff）  └─ 设置（中继地址 / 配对）      │
   └──────────────────────────┬───────────────────────────────────┘
                              │  出站 WebSocket（NDJSON 帧，§3）
                              │  Authorization: Bearer <deviceToken>
                              ▼
   ┌────────────────── 公网中继 relay（唯一需要公网的一方）────────┐
   │  TLS 终止 · 认证 · 多路复用 + id 重映射 · 心跳 · 背压          │
   │  只存 sha256；不解析业务；不落库消息正文                       │
   │  /api/v2/tunnel/device        /api/v2/tunnel/home             │
   └──────────────────────────┬───────────────────────────────────┘
                              │  出站 WebSocket（PC 主动外连，§3）
                              │  Authorization: Bearer <homeToken>
                              ▼
   ┌────────────── 家庭网络（无公网 IP / 不改路由器）───────────────┐
   │  dsh-remote 网关  127.0.0.1:8787（**只绑回环**，§5.5）          │
   │   ├─ 会话镜像：%USERPROFILE%\.dsh（网关只读；续聊经 §7.4 提交） │
   │   ├─ 手机任务：自有 DSH_HOME ← SDK profile 子进程（§7.2）      │
   │   └─ 工作区：白名单 + realpath 越界防护                        │
   │  ↕ 回环通道（§7.4）：session/prompt ↑ / session/follow ↓        │
   │  桌面端 DSH runtime（电脑端自己的执行者，驱动电脑端会话）        │
   └───────────────────────────────────────────────────────────────┘
```

**要点**：手机与 PC **没有任何直达路径**（判据 A 实测：局域网 IP、`10.0.2.2`、主机名全部不可达）；
两侧都只**出站**连中继。因此"不同网络下可用"不需要公网 IP、端口映射或第三方组网。

## 1. 术语与标识

| 名称 | 形态 | 生成方 | 说明 |
|---|---|---|---|
| `homeId` | `home_` + 22 位 Base64Url | 中继 | 一台 PC 在一个中继上的唯一标识 |
| `homeToken` | 32 字节随机 Base64Url | 中继 | PC 隧道凭据；中继只存 `sha256` |
| `pairCode` | 6 位数字 | 网关（本机回环生成） | 一次性、默认 5 分钟；经中继转发给手机 |
| `deviceToken` | `dshr_` + 32 字节 Base64Url | **网关** | 手机 API 凭据；网关与中继都只存 `sha256` |
| `deviceId` | 小写 UUID v4 | 手机 | 沿用 v1 裁定 A4 |
| `streamId` | 1..2^53 整数（JSON number） | 中继 | 一次请求/响应的多路复用标识 |

## 2. 中继 HTTP 端点

### 2.1 `GET /health`（无需认证）

```json
{ "ok": true, "relayVersion": "2.0.0", "apiVersion": 2, "uptimeMs": 12345, "homes": 1, "devices": 2, "relayName": "relay.example.com" }
```

### 2.2 `POST /api/v2/homes`（PC 注册隧道，中继生成凭据）

请求（无需认证，但需携带一次性 `relaySecret`，见 §1 配置）：

```json
{ "relaySecret": "<中继配置里的注册口令，可空>", "homeName": "DESKTOP-XXX", "gatewayVersion": "2.0.0" }
```

响应 `200`：

```json
{ "homeId": "home_9f2c…", "homeToken": "…", "relayName": "relay.example.com" }
```

- `homeToken` **只在本次响应中出现一次**，PC 负责持久化（`config.json` 的 `relay.homeToken`）。
- 同一 `homeName` 重复注册：中继**复用**该 home 记录并**轮换** `homeToken`（旧连接被断开）。

### 2.3 `POST /api/v2/pair/claim`（手机用配对码换设备令牌，中继→PC 转发）

请求：

```json
{ "code": "482913", "deviceName": "Xiaomi 14", "deviceId": "8f3c…" }
```

中继行为：按 `code` 找到 home → 经该 home 的隧道向网关 `POST /api/v2/pair/claim` 转发 → 把网关结果原样返回。

成功 `200`（字段与 v1 保持一致，只多一个 `relay` 块）：

```json
{
  "token": "dshr_9f2c…", "tokenId": "tok_7a1b…", "serverName": "DESKTOP-XXX", "expiresAt": null,
  "relay": { "homeId": "home_9f2c…", "deviceToken": "…", "tunnelUrl": "wss://relay.example.com/api/v2/tunnel/device", "apiVersion": 2 }
}
```

**`relay` 块的存在性是「能力探测」的唯一判据**（裁定）：

| 路径 | `relay` 块 | 说明 |
|---|---|---|
| 经隧道 `/api/v2/pair/claim` | **恒有**（中继注入） | 新 App 用它拿 `deviceToken` 与 `tunnelUrl` |
| 经隧道 `/api/v1/pair/claim` | **恒有**（中继注入） | 老 App 忽略未知字段 → 零影响；新 App 也用它做能力探测 |
| **直连** `/api/v1/pair/claim` | **无** | v1 直连响应体**逐字不变**（向后兼容铁律，见 §4.5） |

- 客户端**不要**用 `health.apiVersion` 判断是否支持中继，用 `relay` 块存在性。
- `relay.homeId` 由中继补；`tunnelUrl` 由中继补；`deviceToken` 由**网关**生成（§1）而中继只存 `sha256`。
- PC 不需要知道自己的公网地址。
- 中继存 `sha256(deviceToken)` 绑定到 `homeId`；同一 `deviceId` 再次 claim → **轮换**旧 `deviceToken` 并吊销其旧连接。

失败：

| HTTP | code | 场景 |
|---|---|---|
| 401 | `pairing_bad_code` | 码错/过期/已用 |
| 403 | `pairing_closed` | PC 未开启配对 |
| 404 | `home_not_found` | 码对不上任何 home（中继侧） |
| 503 | `home_offline` | PC 隧道不在线 |

## 3. 中继 WebSocket 隧道

两个端点，同一套帧协议：

| 端点 | 谁连 | 认证 |
|---|---|---|
| `wss://<relay>/api/v2/tunnel/home` | PC 网关 | `Authorization: Bearer <homeToken>` |
| `wss://<relay>/api/v2/tunnel/device` | 手机 | `Authorization: Bearer <deviceToken>` |

### 3.1 帧类型总表

| 方向 | `t` | 字段 | 语义 |
|---|---|---|---|
| C→S | `hello` | `proto:2`, `role:'home'\|'device'`, `name?` | 首帧，必须最先发 |
| S→C | `ready` | `proto:2`, `role`, `homeId`（device 时含 `homeName`,`homeOnline`） | 准入成功 |
| S→C | `error` | `code`, `message`, `fatal:true` | 拒绝；`fatal` 时中继随后关闭连接 |
| C→S | `req` | `id`, `method`, `path`, `headers`, `bodyB64?` | 请求（device→中继；中继→home） |
| S→C | `res` | `id`, `status`, `headers` | 响应头 |
| S→C | `chunk` | `id`, `dataB64` | 响应体分片（任意次，可 0 次） |
| S→C | `end` | `id` | 本次响应结束（正常） |
| S→C | `abort` | `id`, `reason` | 异常终止（对端断开、home 掉线、超时） |
| 双向 | `ping`/`pong` | `id?` | 心跳；`ping` 30s 无 `pong` 视为死链 |
| C→S | `cancel` | `id` | 取消该请求（SSE 客户端离开时必须发） |
| S→C | `notice` | `kind:'home_offline'\|'home_online'\|'revoked'`, `homeId?` | 状态通知（无需请求） |

### 3.2 多路复用规则

- `id` 由**发起 `req` 的一方**分配，在其连接内唯一且单调递增；响应的 `id` 必须回填同一个值。
- 中继在 **device→home** 方向做 `id` 重映射：把手机侧 `id` 映射为该 home 连接上独立分配的 `id`，避免两个手机撞号。
- 一个 `req` 的生命周期：`req` → (`res` → `chunk`* → (`end`|`abort`))。
- **SSE 长连接**：网关把 SSE 字节流原样作为 `chunk` 推出，`end` 只在流真正结束时发（可能永不发）。
- 上限：单条 `chunk` 的 `dataB64` 解码后 ≤ **256 KiB**；中继对单个 `id` 缓冲不超过 **1 MiB**（超出即 `abort: 'overflow'`）。
- 背压：中继按 WebSocket `bufferedAmount` 反压，> 4 MiB 时暂停读取对端。

### 3.3 错误码

`unauthorized` `forbidden` `home_offline` `not_found` `bad_request` `rate_limited` `too_many_streams` `overflow` `timeout` `internal`

### 3.4 控制面：home 反向调用中继（**裁定**）

`req` 帧**不是单向的**：home 连接也可以用 `req` 帧调用**中继自身**的端点（中继即服务端）。
这是「PC 声明配对窗口」的唯一机制 —— 不去新增 `S→C` 控制帧，复用请求/响应形状。

| 方法 | 路径（中继自身） | 认证 | 说明 |
|---|---|---|---|
| `POST` | `/api/v2/pair/window` | home 连接身份（不必再带 Bearer） | 声明配对窗口：`{code, expiresAt}`；中继建立 `code → homeId` 索引，过期自动清除 |
| `GET` | `/api/v2/pair/window` | 同上 | 查询当前窗口：`{open, expiresAt}` |
| `POST` | `/api/v2/pair/close` | 同上 | 关闭窗口 |

中继对「home 发来的 `req`」的处理顺序：**先查自己的控制面路由表**（上表），未命中才拒绝（home 不得借隧道访问中继的对外管理端点）。
配对窗口默认 TTL 5 分钟，与网关自身配对码 TTL 一致；同一 home 重复声明则覆盖旧码。

**配对码冲突**：6 位数字空间内若新码与仍有效的旧码撞号，中继生成新码返回 `409 {error:{code:'code_conflict'}}`，网关重试（最多 5 次）。

### 3.5 中继行为补充裁定（relay-dev 提问后固化，三方一律遵守）

| 场景 | 中继行为 |
|---|---|
| device 发 `req` 而目标 home 离线 | 回 `res{status:503}` → `chunk`(body = `{"error":{"code":"home_offline","message":"电脑当前离线"}}`) → `end`。**不用 `abort`**，让 TunnelHttp 侧与真实 HTTP 语义一致；同时在该 home 掉线瞬间向所有其 device 推 `notice{kind:'home_offline'}` |
| device 单连接并发流 > 64 | `res{status:429}` → `chunk`(`{"error":{"code":"too_many_streams"}}`) → `end` |
| `chunk` 解码后 > 256 KiB，或单流已缓冲 > 1 MiB | `abort{id, reason:'overflow'}`（此时 `res` 已发出，只能用 abort） |
| `abort.reason` 取值枚举 | `overflow` \| `peer_closed` \| `home_offline` \| `timeout` \| `canceled` \| `internal` |
| home 借隧道访问中继的**对外**管理端点 | **拒绝**（见下表） |

`home_offline` 与 device 自身请求得到的 `503` **两者都要有**：前者供 UI 主动显示「电脑离线」，后者保证请求语义与真实 HTTP 一致。

**device 经隧道被中继拦截的路径白名单（R2 互操作事故后固化）**：

```
/health
/api/v2/homes
/api/v2/tunnel/*
/api/v2/relay/*
/api/v2/pair/*
/api/v1/pair/open
```

**这个名单之外的一切路径都必须放行**，特别是 `/api/v1/*` 的全部业务端点。

> **事故记录（为什么写这么细）**：中继第一版把整个 `/api/v1/` 前缀都拦了，导致经隧道 `GET /api/v1/health` 返回 `403`，
> **直接违反 v1 契约「task 端点全部保留」**——已装机的 v1 App 经隧道后会完全不可用。
> 两侧各自的单元测试都没发现，因为中继侧测试当时按**同一份错误名单**写的（第二次「共用假设自洽」）。
>
> `/api/v1/pair/claim` **必须放行**（v1 App 走的就是它）：中继把 `code` 映射到 homeId 后**转发**给网关的
> `pair/claim` 逻辑处理，语义与 `/api/v2/pair/claim` 完全一致，中继不自己做任何令牌签发。

## 4. 网关 HTTP API（v2 新增；v1 全部保留）

所有端点（除 `health` 与 `pair/*`）要求 `Authorization: Bearer <deviceToken>`。

### 4.1 中继管理（**仅回环**，与 `pair/open` 同源策略）

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v2/relay/connect` | 用配置里的 relay 地址注册并建立隧道；返回 `{ok, homeId, relayName, status}` |
| `GET` | `/api/v2/relay/status` | **直接返回扁平状态对象**（不是 `{ok,status}`）：`{enabled, connected, homeId, relayName, url, lastError, since, reconnects, attempts, inFlight, idBase, stats}` |
| `POST` | `/api/v2/relay/disconnect` | 主动断开隧道（配置保留） |
| `POST` | `/api/v2/pair/open` | 生成配对码并**同时在中继上打开配对窗口**；返回 `{code, expiresAt, relay:{homeId, tunnelUrl} \| null}` |

非回环来源 → `403 forbidden`。**沿用 v1 裁定 A1。**

### 4.2 会话镜像

> **两类会话的"镜像"含义已分叉（§7.4/§7.5/§7.6 优先）**：`source:"computer"` 的**数据源**仍是
> `%USERPROFILE%\.dsh` 的只读镜像，但自本轮起它**不再只读** —— 手机可以提交轮次，由**电脑端 runtime**
> 真实执行（网关不写镜像文件）；而且手机**新建**的任务自 §7.6 起**默认就落在电脑端**。
> `writable`、`driver`、`createdBy` 与 `409 session_busy` 的适用范围见 §4.2 正文与 §7.5/§7.6。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v2/sessions?source=&workspace=&limit=&cursor=` | 会话列表（两类会话合并返回，用 `source` 区分） |
| `GET` | `/api/v2/sessions/{id}` | 单会话元数据 |
| `GET` | `/api/v2/sessions/{id}/transcript?tail=&cursor=&limit=` | 已投影的对话记录（分页，见 §4.2.1；`tail` 取尾部 N 条，`limit`+`cursor` 供手机端「上拉加载更早」） |
| `GET` | `/api/v2/sessions/{id}/turn-index` | **轮次索引**：每一轮在 transcript 消息数组里的区间（v2.9.0，见 §4.2.3） |
| `GET` | `/api/v2/sessions/{id}/events?fromSeq=&tail=` | 原始事件（调试/深度视图） |
| **`POST`** | **`/api/v2/tasks`** | **新建「手机任务」会话并提交首轮**（唯一新建入口）；新增可选字段 `host`（落电脑端 / 落网关自有 home，见 §7.6） |
| `POST` | `/api/v2/sessions/{id}/turns` | 续聊一个会话（**`source:"computer"` 与 `"phone"` 都可**，见 §7.4、§7.5） |
| `POST` | `/api/v2/sessions/{id}/abort` | 中止当前轮次 |
| **`POST`** | **`/api/v2/sessions/{id}/permission`** | **改电脑端会话权限档**（v2.11.0，见 §7.9）：`{"preset":"read-only"\|"workspace-write"\|"danger-full-access"}` |
| `GET` | `/api/v2/sessions/stream` | **SSE**：两类会话的状态变化 + 增量事件（事件带 `source`） |

会话面有**三个各说各事的字段**，客户端**不得互相反推**（`source` 不是"谁发起的"，`driver` 也不是"数据在哪"）：

| 字段 | 取值 | 回答的问题 | 判据 / 来源 |
|---|---|---|---|
| `source` | `"computer"` \| `"phone"` | 会话**数据长在谁家**（镜像根 `%USERPROFILE%\.dsh` vs 网关自有 `DSH_HOME`） | §4.2 数据源；**唯一判据**只认这个字段，不要靠 `origin` 猜 |
| `driver` | `"desktop"` \| `"gateway"` | **现在**由谁执行轮次 | §7.5 |
| `createdBy` | `"phone"` \| `"desktop"` | 这条会话是**谁发起**的 | §7.6（网关自有 `phone-sessions.json`） |
| `permission` | `{currentValue, options[], editable, source, reason}` | 这条会话**当前权限档是什么、能不能改** | v2.11.0，§7.9；旧网关没有该字段 → 客户端显示"未知"，不得默认成 `workspace-write` |

按 `source` 分派时的组合（"手机新建 + 落电脑端"会让三个字段各不相同，这是**正常**的，不是矛盾）：

| `source` | 含义 | 典型 `driver` | 典型 `createdBy` | 可写性 |
|---|---|---|---|---|
| `"computer"` | 电脑端真实会话（`%USERPROFILE%\.dsh`，见 §4.2 数据源） | `"desktop"` | `"phone"`（手机新建落电脑端，§7.6）或 `"desktop"`（电脑端 DSH 自己建的） | **`writable:true`**（桌面端通道可用时，由电脑端 runtime 执行，见 §7.4/§7.5）；`origin === "subagent"` 例外：`false` + `writableReason:"subagent"` |
| `"phone"` | 网关自有 `DSH_HOME` 里的会话（SDK profile 驱动） | `"gateway"` | `"phone"` | `writable:true`（须有活着的运行时；网关重启后旧会话转 `false`，见 §4.2 手机可写性） |

> `host` 的三类错误码、"落电脑端"的确切实现形状与 `createdBy` 的判定见 **§7.6**。

- `access`（**任务级权限档**，用户需求 m00834「可以在任务的时候选择给全部权限还是当前工作区」）：

  | 取值 | 含义 | 网关侧落地 |
  |---|---|---|
  | `"workspace"`（**默认**） | 仅当前工作区：任务只能读写所选工作区，越界读写被沙箱拒绝 | 子进程注入 `DSH_PERMISSION_MODE=workspace-write` |
  | `"full"` | 全部权限：任务可读写这台电脑上任意路径 | 子进程注入 `DSH_PERMISSION_MODE=danger-full-access`（审批策略随之变为 `never`） |

  另接受 DSH 原生别名 `workspace-write` / `danger-full-access`（下划线写法同样接受），实测回显一律规范化为 `workspace` / `full`。
  非字符串或缺省以外**任何未知取值 → `400 bad_request`**（`access 只能是 workspace（仅当前工作区）或 full（全部权限）：<原值>`），
  绝不按高权限方式"猜"；`access` 只影响该会话/该任务，续聊沿用首次创建时的档位。
- `access` 为可选字段：不带该字段的旧客户端 = 默认档（与旧网关行为一致，不构成破坏性变更）。
- 旧网关不支持该字段时，202 响应不带 `access`，客户端应提示"按仅当前工作区执行"。
- `X-Api-Version`/能力协商：能力数组新增 `task.access`（v1 能力数组不变）。
- 新建的会话立即出现在列表里（`source:"phone"`, `writable:true`），随后用 `POST /api/v2/sessions/{id}/turns` 续聊。
- `workspace` 不在白名单 → `400 bad_request`（沿用 v1 语义）。
- `host`（**可选请求字段**，`"desktop"` | `"gateway"`）：手机新建的任务**建在哪里**（语义与实现形状见 §7.6）：

  | 取值 | 行为 | 202 回执关键字段 |
  |---|---|---|
  | 缺省 | 桌面端通道可用 → 落电脑端；未接入 → 退回网关自有 home | 见上两行示例 |
  | `"desktop"` | 在电脑端 DSH 里**新建**会话（`workspace/create` → `session/create`，§7.6） | `source:"computer"` + `createdBy:"phone"` + `driver:"desktop"` + `host:"desktop"` |
  | `"gateway"` | 网关自有 `DSH_HOME`（SDK profile 子进程，§7.2） | `source:"phone"` + `createdBy:"phone"` + `driver:"gateway"` + `host:"gateway"` + `access` |

  **三类错误（逐字，手机端应直接呈现 `message`）**：

  | 场景 | 状态码 / `code` | `message`（逐字） |
  |---|---|---|
  | `host` 取值非法 | `400` `bad_request` | `host 只能是 desktop 或 gateway` |
  | `host:"desktop"` 但缺 `workspace` | `400` `bad_request` | `在电脑端新建任务必须指定 workspace（电脑端是按工作区登记会话的）` |
  | `host:"desktop"` 但网关未接桌面端 | `503` `desktop_unavailable` | `网关未接入桌面端 DSH runtime，无法在电脑端建会话；请改传 host:"gateway"，或先启动电脑端 DSH` |
  | 建会话失败 | `502`（`code` 透传，如 `desktop_error`/`desktop_unauthorized`） | 前缀 `在电脑端创建会话失败：` + 原因 |
  | 会话**已建**、首轮投递失败 | `502`（`code` 透传） | `会话已在电脑端建立（sessionId=…），但首轮投递失败：…` |

  > 末两行的区别很重要：**会话已经真实存在于电脑端了**（`workspace/create` + `session/create` 已成功、也已登记进
  > `phone-sessions.json`），手机端收到该错误时不要以为"什么都没发生"。
- `host:"desktop"` 时 `access` **自 v2.11.0 起生效**：网关在首轮投递前让桌面端执行
  `/permission <preset>`（§7.9），把档位写进该会话日志；成功时 202 回执带
  `access` + `permissionApplied:true` + `permission` 视图，失败时带
  `permissionApplied:false` + `permissionWarning`（任务仍投递，客户端必须提示）。
- 电脑端会话的权限是**会话级**的（`permission/preset` + `sandbox/mode` + `approval/policy` 事件），
  不再等同于桌面端进程的全局默认；`approval/policy: ask` 下触发的审批**自 v2.6.0 起手机端可应答**（§7.7；
  v2.6.0 之前只能回电脑端 UI 批准，那一轮会一直挂住）。`access` 档位这条限制仍只作用于 `host:"desktop"`；
  `host:"gateway"` 的 `access` 语义与 §4.2 权限档表完全不变。

#### 4.2.1 transcript 分页语义（手机端「对话 / 轨迹」分页的契约）

一个长会话的投影可能有上千条消息。手机端**不得**一次拉全量（内存与渲染都无界），
必须按页拉取；本节把服务端已经实现的分页语义固化为契约（用户需求 m00002）。

| 参数 | 含义 | 取值 |
|---|---|---|
| `tail` | 取**尾部** N 条（滚动窗口式：始终是"最新的 N 条"） | 正整数；缺省 `200`，上限 `1000` |
| `limit` | 页大小（配合 `cursor` 使用） | 正整数，经 `clampInt` 收敛到 `1 ~ 1000`；缺省 `200` |
| `cursor` | **排他上界**（消息数组的 offset），返回其**之前**最多 `limit` 条 | 十进制非负整数字符串；非法值按 `0` 处理 |
| `include` | `internal` / `all` 时返回全量（含 system prompt、runtime-context 快照、team 消息） | 缺省过滤掉 `internal` 消息 |

响应（在 §4.2 示例的基础上补齐分页字段）：

```json
{
  "sessionId": "session-88e9459c-…",
  "messages": [ … ],
  "nextCursor": "940",
  "total": 1000,
  "from": 940,
  "to": 1000
}
```

- `from`/`to` 是本页在**过滤后**消息数组里的半开区间 `[from, to)`；`to - from == messages.length`。
- `nextCursor` 是**下一页（更早）**应当传入的 cursor：`nextCursor = String(start)`，`start === 0` 时为 `null`。
  **`nextCursor == null` 是"已到最早"的唯一判据**，客户端不得用 `messages.length < limit` 或
  `已加载条数 >= total` 代替它（窗口被裁剪过、或被 `tail` 截过时两者都会骗人）。
- `total` 是过滤后的消息总数，只用于显示进度（如「已加载 120/1000 条」）。
- **`tail` 与 `cursor` 混用要小心**：`paginate` 的页大小取 `limit ?? tail ?? 200`。
  客户端做「上拉加载更早」时应只传 `limit`+`cursor`，不要同时传 `tail`，
  否则容易出现"服务端按 `tail` 截断、客户端按 `tail` 算游标"的错配。
- 首屏（进入会话）与"追最新"（一轮结束后）都用 `limit=<页大小>`、不带 `cursor`：语义等价于"取尾部一页"，
  且**不带** `tail` 时响应仍会给出 `nextCursor`，客户端据此知道自己能否继续往上翻。
- 向后兼容：不认识 `limit`/`cursor` 的旧网关会忽略它们并返回全量或 `tail` 结果，且**不返回** `nextCursor`。
  此时客户端必须把 `nextCursor` 缺失当作"分页信息不可用"（可以显示"已加载全部"），
  **不得**把它误判成"已经到最早"而丢掉已有的游标（见 `TranscriptPager.pickNextCursor` 的实现约束）。

#### 4.2.2 图片引用字段 `images`（v2.9.0）

会话里的图片**字节不在会话日志里**。日志（`session.v4.jsonl.zstd`）只记录一个**引用**，真实形状（实测）：

```json
{"type":"user/message","seq":9,"time":1792075388873,
 "data":{"content":[
   {"type":"text","text":"这张图里的报错怎么修"},
   {"type":"image","attachment":{"attachmentId":"sha256:591b11a6…6e4ffb","mediaType":"image/png",
                                 "width":64,"height":64,"bytes":6443,"name":"e2e-64.png"}}],
   "source":{"kind":"user"},"role":"user","id":"c6480306-…"}}
```

网关把它投影成 `images` 数组，挂在**三种**消息上：

| 挂在哪里 | 来源事件 | 手机端渲染位置 |
|---|---|---|
| 用户消息 | `user/message` 的 `data.content` | 用户气泡里的图片 |
| 助手消息 | `assistant/message` 的 `data.message.content` | 助手气泡里的图片（罕见，但必须支持） |
| 工具调用 | `tool/result` 的 `data.message.content` → 挂到**对应 toolCall** 的 `images` | 「工具调用」卡里的产物（`read_image`、截图类工具） |

```json
{ "seq": 9, "role": "user", "at": 1792075388873, "turn": 1,
  "text": "这张图里的报错怎么修", "toolCalls": [], "deliverables": [],
  "images": [ { "id": "sha256:591b11a6…6e4ffb", "mediaType": "image/png",
                "width": 64, "height": 64, "bytes": 6443, "name": "e2e-64.png" } ] }
```

| 字段 | 含义 | 缺失时 |
|---|---|---|
| `id` | **内容哈希**，原文照抄自 `attachment.attachmentId`（规范化：统一小写、补 `sha256:` 前缀） | 该图片**整条被丢弃**（形状不对的引用不进数组） |
| `mediaType` | 写入端的声明 | `null` |
| `width` / `height` | 像素尺寸 | `null` |
| `bytes` | 字节数 | `null` |
| `name` | 文件名 | `null` |

**取字节**：`GET /api/v2/attachments/{id}`（§4.6）。`mediaType` 只是**提示**，
真实 `Content-Type` 以该端点响应头为准（服务端按**磁盘字节**嗅探，见 §4.6）：
历史数据里 `mediaType` 可能缺失，也可能与落盘字节不一致。

**向后兼容（§4.5 铁律）**：
- 没有图片块时 `images` **整字段不出现**（不是 `[]`）—— 老客户端解析路径完全不受影响；
- 旧网关不认识这个字段，直接不下发；客户端**不得**因为 `images` 缺失就认为"这一轮没图"
  或拒绝渲染文本，只应退化成现状（显示 `[图片] alt` 一类占位符）；
- `toolCalls[].images` 与消息级 `images` 是**同一种形状**（同一个投影函数产出）。

失败面（客户端必须能处理）：

| 场景 | 表现 | 客户端应有的行为 |
|---|---|---|
| 引用形状不合法 | 该条不出现在 `images` 里 | 与"没有图"相同，不要显示坏图 |
| 对象已不存在（日志被复制到别的机器 / 对象库被清理） | 端点 `404 not_found` | 渲染占位符，**不要**无限重试 |
| 对象超过 8 MiB | 端点 `413 attachment_too_large` | 提示"图片过大，请在电脑端查看"，与 404 区别对待 |
| 旧网关（无 `attachments` 能力） | 端点 `404`（未知接口） | 先看 `GET /api/v2/health` 的 `capabilities` 有没有 `attachments` |

#### 4.2.3 轮次索引 `GET /api/v2/sessions/{id}/turn-index`（v2.9.0）

手机端本地只加载最近一页消息（§4.2.1），要做到「点一下**第 12 轮**就跳到那一轮」，
就必须先知道每一轮在消息数组里的位置。这个端点只回**索引信息**（每轮一条、文案服务端截断），
客户端拿 `toIndex` 去调**既有**的 `GET /transcript?cursor=<toIndex>&limit=60` 即可，
**不需要**新增加载路径，也不需要客户端自己解析事件。

```json
{ "sessionId": "session-88e9459c-…", "total": 42, "totalMessages": 733,
  "turns": [
    { "turn": 1, "fromIndex": 0, "toIndex": 7, "at": 1760000000000,
      "userText": "帮我看看构建失败的原因", "assistantText": "定位到 AGP 版本不匹配…",
      "steps": 3, "toolCalls": 5 }
  ] }
```

| 字段 | 含义 |
|---|---|
| `sessionId` | 会话 id |
| `total` | `turns` 数组长度 = **有消息归属的轮次数**（与 `meta.turns` 可能不等，见下） |
| `totalMessages` | **过滤后**的消息总数（与 `/transcript` 的 `total` 同一个数） |
| `turns[].turn` | 轮号（`turn/start` 的 `turn`） |
| `turns[].fromIndex` | 该轮第一条消息在 `/transcript` 消息数组里的下标（0 基，**闭**） |
| `turns[].toIndex` | 该轮**之后**的第一个下标（**开**）。`[fromIndex, toIndex)` 恰好是这一轮 |
| `turns[].at` | 该轮第一条消息的 `at`（毫秒） |
| `turns[].userText` | 该轮**第一条有正文的** user 消息，UTF-8 安全截断 ≤200 **字节**（中文≈66 字） |
| `turns[].assistantText` | 该轮**最后一条有正文的** assistant 消息，同样截断（取末尾是因为长轮次的结论在最后） |
| `turns[].steps` | 该轮不同 `step` 的个数（缺 `step` 的消息不计） |
| `turns[].toolCalls` | 该轮各消息 `toolCalls` 长度之和 |

**下标空间的定义（这是本端点的全部价值，务必逐字实现）**：
`fromIndex`/`toIndex` 是**与 `/transcript` 完全同一套投影、同一种 `internal` 过滤**之后的
消息数组下标。服务端两条端点都只经由同一条投影路径取消息（`SessionMirror` 内部的
`#projectionOf`），**不允许**各写一套解析 —— 否则索引会指到别的消息上，客户端表现为
"跳过去少一条/多一条"，而这种错位几乎无法从现象倒推回原因。

**没有 `turn` 归属的消息**（会话开头的系统注入、`turn/end` 之后的收尾合成消息、
`deliverables/presented` 兜底生成的那条、待办卡）**不进任何一轮**：它们让区间端点落在
非对话消息上时，客户端按 `toIndex` 取页会莫名其妙多/少一条。宁可让区间之间留缝，
也不要把它们塞给"当前轮"。推论：`total`（有归属的轮数）**可能小于** `meta.turns`
（`turn/start` 的计数）—— 界面上显示"共 N 轮"请用 `GET /sessions/{id}` 的 `turns`，
用 `turn-index` 的 `turns[]` 做跳转。

**参数与分页**：
- `?workspace=<白名单工作区绝对路径>`：与 `/transcript`、`/sessions/{id}` 同一个上下文参数；
- `?include=internal|all`：与 `/transcript` 同义（此时下标空间也随之一致地变成含 internal 的数组）。
  **两个端点必须传同一个 `include`**，否则下标对不上（这是使用上的硬约束，不是服务端能兜住的）。

**失败表**：

| 场景 | 状态码 / `code` | 说明 |
|---|---|---|
| 正常 | `200` | 没有轮次的会话返回 `turns: []`（不报错、不返回 `null`） |
| 会话不存在 | `404` `session_not_found` | 与 `/transcript` 同码 |
| 未认证 | `401` `unauthorized` | 不在 `PUBLIC_ROUTES` 里 |
| 方法不对 | `405` | 只允许 `GET`；**`POST /api/v2/sessions/{id}/turns` 是另一条路径**（发一轮），本端点没有碰它 |

> 能力协商：`GET /api/v2/health` 的 `capabilities` 新增 `session.turnIndex`；
> 缺失即旧网关（客户端应隐藏"跳转轮次"入口，而不是显示一个点了没反应的按钮）。

`POST /api/v2/sessions/{id}/turns` 请求/响应：

```json
// 请求
{ "prompt": "把测试跑一遍", "clientTurnId": "8f3c…" }
// 202 响应（source/driver 自 v2.4.0 起恒显式下发，见 §7.5）
{ "accepted": true, "sessionId": "session-88e9459c-…", "turnId": "turn_…", "fromSeq": 1778,
  "source": "computer", "driver": "desktop" }
```

> `driver` 在本节是**同一个字段、同一套取值**，贯穿 `GET /sessions`、`GET /sessions/{id}`、
> `POST /turns` 202 回执、`POST /abort` 200 回执**四处**（实现见 `tools/dsh-remote/lib/http.mjs:235-236` 与
> `lib/session-runner.mjs:72-73` 的同名常量），**不再有"通道标识"与"会话属性"同名不同域的问题**：
> 客户端只按 §7.5 判定即可，`source` 仍只表示数据来源。

#### `POST /turns` 的 `content`（ContentBlock[]，可选，v2.8.0 起）

`prompt` 仍是必填的非空字符串（它同时是任务标题、列表摘要与旧客户端契约）。带图片时**额外**传 `content`：

```json
// 请求（带图）
{ "prompt": "这张图里的报错怎么修",
  "clientTurnId": "8f3c…",
  "content": [
    { "type": "text",  "text": "这张图里的报错怎么修" },
    { "type": "image", "mediaType": "image/jpeg", "data": "<base64，无 data: 前缀>", "name": "IMG_20261015.jpg" }
  ] }
```

| 约束 | 值 | 超限时 |
|---|---|---|
| 单图解码后字节 | ≤ `716_800`（700 KiB） | `400` `content[i] 解码后 N 字节，超过单图上限 716800 字节（700 KiB）` |
| 图片张数 | ≤ `4` | `400` `图片数量超过上限：一轮最多 4 张（收到 N 张）` |
| 整包 base64 字符总量 | ≤ `1_000_000`（≈976.6 KiB） | `400` `图片总量超过单次请求预算（约 1 MB base64），请减少图片数量或压缩后再发` |
| `mediaType` | `image/png` / `image/jpeg` / `image/webp` / `image/gif` | `400`，不做内容嗅探 |
| `data` | 严格 base64（长度 4 的倍数、只允许 `A-Za-z0-9+/=`） | `400`，**不接受** `data:` 前缀 |

- 走 `source:"computer"`（桌面端 runtime 通道）时 `content` 原样转成回环通道 `session/prompt` 的
  `content`（§7.4），图片以**内联 base64** 交给电脑端 DSH：runtime 落盘到
  `$DSH_HOME/attachments/v1/objects/<sha256 前 2 位>/<sha256>`，转录里成为
  `{type:'image', attachment:{attachmentId:'sha256:…', mediaType, bytes, width, height}}`，agent 可用 `read_image` 读它。
  **实测闭环**：1×1 PNG（70 B）与 1400×1000 PNG 均 202 + `driver:"desktop"`，转录出现 `read_image` 调用与实体图片。
- **只支持 `source:"computer"` 的会话**：`source:"phone"`（网关自持 SDK 通道）带 `content` 时 `400`
  `图片只能发给电脑端会话（该会话由网关自持，图片通道未覆盖）`；纯文本请求两条通道行为不变。
- 校验顺序（`tools/dsh-remote/lib/http.mjs:170-242` `validateTurnContent`）：先按 `type` 数图片张数 → 逐块
  结构/mediaType/严格 base64 → 单图 ≤700 KiB → 整包 ≤1_000_000 字符。所有消息都带 `content[i]` 下标。
- **刻意不修的边界**：请求体在**网络层**就超过 `limits.maxBodyBytes`（`1_048_576` B）时，
  `readJsonBody` 不读体、直接 `413 payload_too_large` + `Connection: close`，客户端只会看到连接被重置
  —— 拿不到上面任何一条结构化 400。所以**客户端必须按同值做本地预校验**（Android 侧
  `DshApiV2.bodyWithinBudget`，量的是 UTF-8 **字节数**，因为中文一字 3 字节）。
  放宽 `maxBodyBytes` 不在选项内：那是网关与中继两侧的契约硬性承诺（运维配置）。
- 兼容性：`content` 缺省 / `null` / `[]` 时行为与本条出现前**逐字一致**（`validateTurnContent` 返回
  `content: null`，`runner.submit` 不读该键）；不认识 `content` 的旧网关会忽略它、只按 `prompt` 执行，
  此时图片静默丢失 —— 客户端应校验回执里的 `driver`/`source`，不要假定图片一定送达。

- `202` 的语义对两类会话一致：手机提交的轮次**真的在 PC 上执行**，事件经 SSE 回流（§4.2 事件流、§5.3）。
  电脑端会话的执行方是**电脑端 runtime**，不是网关自有的 SDK 子进程（§7.4）。
- `409 conflict` + `{error:{code:"session_busy", message:"该会话正由电脑端驱动，请在电脑端继续或在手机端新建会话"}}`：
  **适用范围已收窄**——只在该会话**正被占用**时返回（`live:true` / 网关侧租赁未释放 / 运行时已结束），
  **不再**对 `source:"computer"` 一概返回（§7.4 起该通道可续聊）。对 `source:"phone"` 的会话语义不变：
  其 `live` 时返回，防止两处同时写同一会话。
  > 旧文案「对 `source:"computer"` 的会话任何 `POST /turns` 都返回此码」自 §7.4 起**失效**；文案逐字保留，仅适用范围收窄。
- 续聊实现：`source:"computer"` 走桌面端 runtime 通道（§7.4）；`source:"phone"` 走长驻 SDK profile 子进程（§7.2）。
  两条路径的事件都实时投影后经 SSE 推送。
- `503 unavailable` + `{error:{code:"session_taken"}}`：该会话已被本进程的另一个轮次占用。

`GET /api/v2/sessions/stream`（SSE）：

```
event: session.updated    data: {"sessionId":"…","source":"computer","updatedAt":…,"live":true}
event: turn.started       data: {"sessionId":"…","source":"phone","turn":3,"fromSeq":1778}
event: message.delta      data: {"sessionId":"…","seq":1779,"role":"assistant","text":"…"}
event: tool.call          data: {"sessionId":"…","seq":1780,"name":"pwsh","args":{…}}
event: tool.result        data: {"sessionId":"…","seq":1781,"isError":false,"result":"…"}
event: turn.ended         data: {"sessionId":"…","turn":3,"reason":"completed"}
event: session.created    data: {"sessionId":"…","source":"phone","workspace":"…"}
event: heartbeat          data: {"at":…}
```

- **一条流覆盖两类会话**：每条事件都带 `sessionId`，`session.updated`/`turn.started`/`session.created` 还带 `source`；
  客户端按 `source` 分流（不懂的 `source` 值应忽略而不是报错）。
- **`?sessionId=<会话 id>`（可选参数）**：只推**该会话**的事件；**不传 = 全局流**（即上面这条主用法：
  一条流覆盖两类会话，客户端按事件里的 `sessionId`/`source` 自行分流）。
  **不带 `sessionId` 的全局事件（如 `heartbeat`）在两种用法下都仍会下发**。
  实测（2026-10-14，真机探针 marker `e2e-ssfilter-1`，两个临时桌面临时会话 A/B）：`?sessionId=A` 的流 **6 帧全是 A**
  （B = 0、其它会话 = 0）；同时**不传**参数的全局流 **12 帧 = A 6 + B 6**。
  该参数是**纯新增可选参数**，不递增 `X-Api-Version`；**不传时行为逐字不变**（手机端 `ConsoleStreams.path()`
  只带 `fromSeq`/`tail`，走的就是全局流，不受影响）。
  仓库内**回归钉子**：`tools/dsh-remote/test/v2-desktop.test.mjs`
  「`v2/desktop：?sessionId= 的 SSE 流只收本会话事件（全局流仍全部会话都收）`」（D-07 的永久证据，
  含"未过滤流上先到的是先投的 B"的正对照，避免竞态假绿；该文件随网关单测冻结跑数 **189 / 189**
  全绿，`fail 0` / `skipped 0`，2026-10-14）。
- 客户端用 `Last-Event-ID`（= 事件 `seq`）或 `?fromSeq=` 续传；服务端回放 ≥ `fromSeq` 的事件。
  **注意**：新开一条流并传 `?fromSeq=0` 会**回放历史**（包括此前轮次的 `turn.ended`）—— 这是契约行为，
  **不是重复投递缺陷**；探针与客户端必须按 `turn` 号或 `seq` 计数，不得按"收到的事件条数"做断言
  （2026-10-14 探针 `e2e-takeover-final3` 即因此出现计数假失败，改为按 `turn` 号计数后 `e2e-takeover-final4` 33 项全绿）。
- **客户端必须按「会话 + 轮次」去重 `turn.started`**：网关驱动的每一轮在总线上**恒有 2 条** `turn.started`
  ——① 网关入队时的本地回执（带 `fromSeq` + `turnId`）；② DSH 的 `turn_start` 经翻译后的那条；
  `turn.ended` 仍然唯一。**这是设计，不是缺陷**：`lib/http.mjs:1220-1230` 记录了"若不掐掉观望订阅会变成 3 条"，
  Android 客户端早已在 `android/app/src/main/java/com/deepseek/dshremote/data/ConsoleRepository.kt:844-851` 显式去重
  （会话状态靠 `markLive` 覆盖，天然幂等）。**不得把 `turn.started` 的条数当作轮次计数**，也不要"修"它。
- 心跳 15s。

### 4.3 工作区

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v2/workspaces` | 白名单工作区（沿用 v1）+ 每个工作区的 git 状态摘要 |
| `GET` | `/api/v2/workspaces/files?path=&depth=&showHidden=` | 目录树（默认 `depth=1`，`depth` 上限 4） |

| `GET` | `/api/v2/workspaces/search?q=&path=&limit=` | 文件名/内容的轻量搜索 |

**电脑端工作区同步（v2.11.0）**：`GET /api/v2/workspaces` 的列表 = **配置白名单 ∪ 电脑端
`<desktopHome>/storages/workspace.json` 里已登记的工作区**。每个条目新增：

| 字段 | 说明 |
|---|---|
| `source` | `"desktop"`（来自电脑端登记）\| `"config"`（只在网关配置里） |
| `title` | 电脑端显示标题（可自定义/重名；`label` 在有 title 时与它一致） |
| `workspaceId` | 电脑端稳定 id（仅 `source:"desktop"`） |
| `sessionCount` | 电脑端该工作区会话数（仅 `source:"desktop"`） |

响应顶层新增 `desktopWorkspaces:{enabled,home,count,lastRefreshAt,error}`（诊断用）。
同步周期由 `desktopWorkspaces.pollMs` 控制；`GET /workspaces` 会顺手重读一次，所以电脑上刚建的
工作区通常立刻可见。**安全边界**：只合并该 home 里用户**自己登记过**的目录，不扫描磁盘；合并后
仍走本节的 realpath/白名单校验。从 `workspace.json` 删除后，下一次列表请求即从有效白名单移除，
文件接口同步变为 `403 workspace_outside`。

**v1 冻结**：`GET /api/v1/workspaces` 仍然只返回配置白名单，不合并电脑端工作区、不带上表新字段。
已交付的 v2.10.0 手机端读的就是它，条目集合变化属于 v1 语义变更（见 §0 的向后兼容铁律）。
电脑端工作区只经 v2 暴露。

> **`workspace` 参数（2026-10-15 起显式化）**：5 个工作区端点都接受可选的 `?workspace=<白名单工作区绝对路径>`，
> 表示"这次请求以哪个工作区为上下文"。**客户端应当显式带上它**；缺省时网关按下面的反推规则兜底（见下）。
> 显式传了 `workspace` 就以它为准 —— **不会**因为 `path` 落在别的工作区而"救回来"，仍按越界拒绝。

**路径安全规则（硬性）**：所有 `path` 参数必须是白名单工作区内的**绝对路径**或相对该工作区的相对路径；
网关 `realpath` 解析后必须仍落在白名单内，拒绝 `..` 穿越、符号链接逃逸、UNC 路径；
越界 → `403 forbidden`（`{error:{code:"workspace_outside"}}`）。

**缺 `workspace` 时的反推（2026-10-15 新增，兼容旧客户端）**：老版本客户端只发绝对 `path`、不发 `workspace`，
网关曾因此把请求回落到 `defaultWorkspace`，于是"选中的是另一个白名单工作区"时**必然**误判越界 ——
真机现象就是 `403 路径越界（不在工作区内）：D:\Workspace\插件`。现在的规则：

1. `path`（或 `file`）是**绝对路径**且其 `realpath`（叶子不存在时取最近的已存在祖先）落在某个白名单工作区内
   → 用**最长匹配**的那个工作区当上下文（白名单里可能同时有 `D:\ws` 与 `D:\ws\sub`）；
2. 其余情况（相对路径、工作区之外的路径）→ 仍回落到 `defaultWorkspace`，**不扩大任何权限**
   （反推只可能返回"白名单里真实存在的工作区"，越界路径依旧 `403 workspace_outside`）。

`GET /api/v2/workspaces/files` 响应：

```json
{ "workspace": "D:\\Workspace\\dsh_android", "path": "D:\\Workspace\\dsh_android",
  "entries": [ { "name": "android", "path": "…\\android", "type": "dir", "size": null, "modifiedAt": 1791… },
               { "name": "README.md", "path": "…\\README.md", "type": "file", "size": 20565, "modifiedAt": 1791… } ],
  "truncated": false }
```

`entries[].type`：`dir` | `file` | `symlink` | `other`。单目录上限 2000 条，超出 `truncated:true`。

`GET /api/v2/workspaces/changes` 响应：

```json
{ "workspace": "D:\\Workspace\\dsh_android", "vcs": "git", "branch": "main",
  "changed": [ { "path": "tools/dsh-remote/lib/http.mjs", "status": "M", "staged": false,
```

### 4.5 向后兼容铁律（Lead 裁定）

**`GET /api/v1/health` 的 `apiVersion` 必须恒为 `1`。** 它是「v1 端点的版本号」，**不是**「网关支持的最高版本」。
已交付的 v1 Android 客户端用它判断兼容性，一旦读到大数可能直接判定不兼容而拒绝连接 ——
这是本轮唯一会伤到**已装机客户端**的风险点。

v2 能力改用**新增**字段表达（老客户端忽略未知字段，天然安全）：

```json
{ "ok": true, "apiVersion": 1, "supportedApiVersions": [1, 2], … }
```

- 请求头 `X-Api-Version: 2` 由 v2 客户端发送；网关对 `1` 与 `2` 都要接受。
- 任何字段**只能新增，不能改名或删除**；删除/改名必须递增主版本并另立端点路径。
- 本轮新增的 `driver` 属**纯新增响应字段**（§4.2）：不递增 `X-Api-Version`（仍为 `2`），旧客户端忽略即可；
  缺失时客户端按 `source` 推导（§7.5）。
- 必须有回归用例锁住 `apiVersion === 1` 且 `supportedApiVersions` 存在。

### 4.6 附件对象库（v2.9.0）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v2/attachments/{id}` | 按**内容哈希**取回一个附件对象的原始字节（图片） |

**为什么需要这一层**：会话日志里只有 `{type:'image', attachment:{attachmentId:'sha256:…'}}` 这样的
**引用**，字节落在**电脑上**的内容寻址对象库里
（`<DSH home>/attachments/<版本目录>/objects/<sha256 前 2 位>/<完整 64 位 hex>`，文件**无扩展名**）。
手机拿不到那个文件系统 —— 本端点就是"哈希 → 字节"的唯一转换点，没有它手机只能显示 `[图片]` 占位符。
写盘的那一侧是 §7.4 的桌面端 runtime（`POST /turns` 的 `content` 内联 base64 由它落盘，见 §4.2 `content` 小节）。

**路径参数 `id`**：

| 写法 | 是否接受 | 说明 |
|---|---|---|
| `sha256:<64 位小写 hex>` | ✅ | **规范形式**，客户端应当用这个 |
| `<64 位 hex>` | ✅ | 容错（客户端丢过前缀；实测日志里也出现过） |
| 大写 / 混写 hex | ✅ | 统一转小写后匹配 |
| `sha256%3A<hex>` | ✅ | 冒号被百分号编码（URL 路径里常见的转义），两种都要能命中 |
| 其它任何形状 | ❌ `400 bad_request` | 消息里写明期望形状；`..`/分隔符/盘符/UNC **一律拒绝**（安全红线） |

**响应（200）**：

```
HTTP/1.1 200 OK
Content-Type: image/png                     ← 按**磁盘字节**嗅探，不是日志里的 mediaType
Content-Length: 246042
Cache-Control: private, max-age=31536000, immutable
X-Api-Version: 1
```

- `Content-Type` 由**魔数嗅探**得出（PNG `89 50 4E 47`、JPEG `FF D8 FF`、GIF `GIF8`、WEBP `RIFF....WEBP`），
  认不出给 `application/octet-stream`。**为什么不信日志里的 `mediaType`**：它是写入端的声明，
  历史数据里可能整个 `attachment` 只有 `attachmentId`（没有 `mediaType`），也可能与落盘字节不一致
  （复制/转码过的对象）；而对象库文件名是内容哈希、**无扩展名**，`extname()` 那条路根本走不通。
- `Cache-Control: private, max-age=31536000, immutable`：内容哈希寻址 ⇒ **同一个 id 的字节永不变**，
  可以放心缓存一年；`private` 是因为它受 Bearer 保护（共享缓存/反向代理不得留存）。
- 响应体是**原始字节**（不是 JSON、不是 base64）。服务端按流发送，客户端可边收边渲染。
- `X-Api-Version: 1`：与其余 v2 端点**逐字一致**（都回 `config.apiVersion`）。这个头按 §4.5 是
  "v1 端点的版本号"，不是"端点属于第几代"，所以并不因为本端点是 v2.9.0 新增就回 2
  （早先的草案曾写 2，会让它成为全网关唯一的孤例，已改回）。**能力协商一律看
  `GET /api/v2/health` 的 `capabilities`**（本端点 = `attachments`），不要解析这个头。

**失败表**：

| 场景 | 状态码 / `code` | `message` 要点 |
|---|---|---|
| id 形状非法（含 63/65 位 hex、非 hex、含 `..`、含分隔符） | `400` `bad_request` | 写清期望形状：`sha256:<64 位小写十六进制>` |
| 所有搜索根里都没有这个对象 / 命中的不是普通文件 | `404` `not_found` | `附件不存在：sha256:…` |
| 对象存在但**超过 8 MiB** | `413` `attachment_too_large` | 报出实际上限与真实字节数 |
| 未认证 / 令牌失效 | `401` `unauthorized` | 与 sessions/workspaces **同档**，不在 `PUBLIC_ROUTES` |
| 方法不是 GET | `405` | 只允许 `GET` |
| 旧网关（无该端点） | `404`（未知接口） | 先查 `capabilities` 里有没有 `attachments` |

**为什么 413 不并进 404**：客户端对两者的处理**必须不同** ——
404 是"这条引用坏了"（渲染占位符即可，可长期记住这个负结果）；
413 是"图太大，网关不愿意服务"（应提示用户去电脑端看，**不该**被当成缓存命中的负结果）。
8 MiB 这个上限的由来：中继侧那条 1 MiB 是**单条隧道流的未刷出积压**上限（背压阈值），
**不是响应总量** —— 图片是按流分帧发过去的，只要生产者不一次性把整个文件怼进队列就不会撞它
（实现用 `fs.createReadStream` 让 Node 自己按 highWaterMark 拉，天然满足）。
真机实测的单张截图是 71 KB~320 KB（1080×2340 PNG），压到 1 MiB 会让长截图莫名其妙取不到；
8 MiB 是**防内存/流量放大**（手机端会把响应读进内存渲染）。

**搜索根与顺序**（命中即返回，重复根去重）：

1. `config.dsh.sessionsHome`（网关自有 home —— 手机发的图由它落盘，命中率最高）；
2. `config.mirror.resolvedHome`（默认 `%USERPROFILE%\.dsh`，电脑端真实会话与 `read_image` 的产物）；
3. `config.desktop.dshHome`（桌面端通道显式配置的 home，缺省与第 2 项同值）。

版本目录（实测 `v1`）用 `readdir` **探测**而不是写死：DSH 升级后目录名可能变，
写死会让所有图片在某次升级后集体 404（这种故障极难从现象倒推回原因）。
同一个 id 在多个 home 里存在时**字节必然相同**（sha256 寻址），所以顺序不产生语义差异，只影响 I/O 次数。

**安全（安全红线）**：

- 附件 id 是**内容哈希**，只有读到过会话记录的人（= 已配对设备）才知道它。
  网关**不做**按会话的二次授权：已配对设备本来就能读所有会话与工作区（§4.2/§4.3），
  再叠一层"这个附件属不属于这条会话"只会给出一种虚假的安全感（引用会被转发/复制）。
- 但**能读什么**必须卡死：id 直接参与拼路径，服务端用
  `ATTACHMENT_ID_RE = /^sha256:[0-9a-f]{64}$/` 严格校验，且对象库两级目录都用 `readdir` 的结果比对，
  **绝不把用户输入拼成路径段**。任何"支持更多 id 形式"的放宽都等于打开对象库以外的任意文件读取。
- 本端点**不在** `PUBLIC_ROUTES`：与 sessions/workspaces 同档，必须带 Bearer 令牌。

**能力协商**：`GET /api/v2/health` 的 `capabilities` 新增 `attachments`；
缺失即旧网关（客户端应把图片渲染成占位符，而不是反复请求一个必然 404 的路径）。

### 4.7 模型目录 `GET /api/v2/models`（v2.10.0）

手机端「选模型」的目录。**回体顶层恰好六个键**（多一个是缺陷；少一个客户端按缺失降级）：

| 键 | 类型 | 语义 |
|---|---|---|
| `ok` | `true` | 端点自身成功。**目录降级时也是 `true`** —— 降级不是错误，见下 |
| `source` | `"desktop"` \| `"config"` | 目录来自电脑端 DSH runtime，还是退到网关配置里的那一项 |
| `default` | `{provider, model, reasoningEffort}` | 三项各自可为 `null`。`source:"desktop"` 时 `reasoningEffort` **不会**回落成网关配置值（电脑端没给＝没给） |
| `routableProviders` | `string[]` | 电脑端**实际能路由到**的 provider。与 `groups` **不是一回事**：某个 provider 可能没有任何可选模型却仍可路由 |
| `groups` | `[{id, name, models:[…]}]` | `models` 为空的组**被丢弃**；模型 `{id, name, description?, reasoning?:{efforts:[{id,name,description?}], defaultReasoningEffort?}}` |
| `failures` | `[{id, name, message}]` | 电脑端报的「不可用」清单，**原样透传**；`id`/`name`/`message` 都保证非空 |

**降级是正常路径，不是 5xx**：`desktop.enabled=false`／未接入、RPC 不可达、RPC 回 `ok !== true`、
回体不是对象 —— 一律 `200` + `source:"config"`（`default` 取 `dsh.provider`/`dsh.model`/`dsh.reasoningEffort`，
`groups:[]`、`routableProviders:[]`），并**必须**在 `failures` 里留一条
`{id:"desktop", name:"电脑端", message:"<这一次为什么降级>"}`（取值逐字：
`网关未接入桌面端 DSH runtime（desktop.enabled=false 或未配置）`、`<error.code>: <error.message>`、
`桌面端未实现 modelCatalog`）。

> `failures` 那一条**不能省**：手机端只有它能解释「为什么列表里只剩一个模型」。
> 只打日志等于让用户永远看不出是**电脑端没连上**，而不是网关把目录丢了 —— 这正是本端点要避免的失败模式。
> 降级原因**每次现造**，不要共用常量对象：将来任何缓存/复用都会把 A 请求的原因显示到 B 请求上。

本端点与 `attachments` 同档：**不在** `PUBLIC_ROUTES`，必须带 Bearer 令牌；
`X-Api-Version` **不递增**（仍为 `2`，§4.5 纯新增）；`capabilities` 新增 `models`。

每任务模型选择（`POST /api/v2/tasks` 的三个字段）见 §7.8。

## 5. 实现约束（三方都必须遵守）

### 5.1 零第三方依赖
网关与中继**只用 Node 内置模块**（`node:http` `node:https` `node:crypto` `node:zlib` `node:fs` `node:child_process` `node:os` `node:path` `node:net` `node:tls`）。
WebSocket 服务端/客户端**自己实现**（RFC 6455 握手 + 帧编解码，够用即可：仅文本帧、无压缩、需支持分片与 ping/pong/close）。
Node 版本以 `D:\DSH\resources\runtime\primary-runtime\dependencies\node\bin\node.exe`（v24.21.0）为准。

### 5.2 Node 内置 zstd 读会话
`node:zlib` 的 `zstdDecompressSync` **只解第一帧**。DSH 会话是**多帧追加**文件，
必须按帧边界切分后逐帧解压再拼接（实现见 `.runtime/zstd-probe.mjs` 的 `decompressMultiFrame`，
该实现已在真实 1153 帧会话上验证：1,598,845 B → 4,880,092 B / 1779 事件）。
**禁止**直接把整个文件丢给 `zstdDecompressSync`。

### 5.3 会话续聊的真实性要求
`POST /api/v2/sessions/{id}/turns` 必须**真的续聊该 DSH 会话**，
不得自行拼历史。已实测：同一 session 第二轮能记住第一轮的上下文（`cacheReadTokens` 命中）。

两类会话的"真实"判据不同，都要满足：

- `source:"phone"`（网关自有会话，原路径）：走 `--session-id` 恢复既存会话（§7.2）。
- `source:"computer"`（电脑端会话）：**必须由电脑端 runtime 执行**（§7.4），网关不得把该轮改成
  "解析历史 + 自己重放"；判据是轮次结束后**电脑端 UI 同步可见**该轮、且 `session/list` 的
  `sessionStats`（turns/steps/decodeTokens）随之增长（§7.4 实测形状）。

### 5.4 `live` 判定
会话目录内 `session.v4.jsonl.zstd` 的 mtime 在 **60s** 内 → 视为 `live`。
网关自己拉起的轮次额外维护内存中的占用表（更强的信号）。

### 5.5 安全红线
1. 网关 HTTP **只绑 `127.0.0.1`**；即使 `config.host` 被写成 `0.0.0.0`，v2 的 relay 功能也必须拒绝启动并给出明确错误（防止把无认证的 API 暴露到局域网/公网）。
2. 中继**只存 `sha256`**；日志里 `homeToken`/`deviceToken`/`pairCode`/`Authorization` 一律脱敏为前 4 位 + `****`。
3. 中继**不落盘消息正文**；只有内存中的连接与流表。
4. 手机端**不得**信任系统证书链之外的实现细节：**不提供** App 内安装自签 CA / "信任自签证书"开关
   （需求 FR-15 / O8 —— 最终实现选择了直接不实现该开关，而不是"默认关闭"）。因此 release 变体只能连接
   系统信任链可校验的正式证书（`wss://` + LE 证书，无域名可用 LE **IP 地址证书**）；自签与明文 `ws://`
   仅限 debug 变体与本机/内网联调（`cleartextTrafficPermitted` 只在 debug 变体放开）。
5. `pair/open` 与 `relay/*` 管理端点**只接受回环来源**。

### 5.5.1 路径规范化与「仅回环」在隧道下失效（**安全级裁定，务必实现**）

> **事故**：中继按字面路径判前缀被绕过，且网关侧「仅回环」检查在隧道路径上**形同虚设**。
> 任一方单独修都不够 —— 两层都要防。

**根因**：`new URL(req.url, base)` 会**折叠点段与百分号编码**，`url.pathname` 已是规范化结果；
而经隧道进来的本机 HTTP 请求，`req.socket.remoteAddress` 天然是 `127.0.0.1`，所以"只接受回环来源"这条判定
**在隧道路径上完全无效**。Lead 用网关自身导出的 `routeOf` 独立复现（4 种写法全部命中管理路由）：

```
"/api/v2/relay/status"        -> route=relayStatus   （基线）
"/x/../api/v2/relay/status"   -> route=relayStatus   ← 绕过
"/%2e%2e/api/v2/relay/status" -> route=relayStatus   ← 绕过
"/api/v2/relay/./status"      -> route=relayStatus   ← 绕过
"/x/../api/v2/pair/open"      -> route=pairOpenV2    ← 绕过
```

**影响**（任何**已配对手机**经隧道即可）：读 `relay/status`（信息泄露）、`POST relay/disconnect`（远程断隧道 = DoS）、
`POST pair/open`（自行开配对窗口 = 越权提权）。

**强制实现（两层都要）**：

| 层 | 要求 |
|---|---|
| 中继 | 所有管理面/控制面判定基于**规范化后**的 pathname（WHATWG URL 折叠点段与百分号编码、`\`→`/`）；字面路径做二次判定；协议相对路径 `//host/x` 直接 400 |
| 网关 | ① 路由判定前校验「折叠后的 pathname」与「原始 path」规范化一致，不一致 → `400 bad_request`；② **不得**把"来源是回环"当作管理端点的授权依据 |

**隧道路径的信任模型（网关侧）**：relay-client 把手机请求转成本机 HTTP 时，加内部标记头（如 `x-dsh-tunnel: 1`），
**并在转发前剥掉客户端自带的同名头**（否则可伪造）；`relayConnect`/`relayStatus`/`relayDisconnect`/`pairOpenV2`/`pairOpen`
**一律拒绝带隧道标记的请求** —— 即「这些端点手机永远不该碰」，与来源 IP 无关。

**回归用例（必须）**：4 种绕过写法全部 400/404 且不命中管理路由；带隧道标记打管理端点 → 403；
客户端伪造该头直连不得获得特权；正常 `source:"phone"` 业务端点不受影响。

**推广约束**：**禁止用前缀/包含关系做安全判定**。中继侧已因此出错三次
（`/api/v1/` 破坏 v1 兼容、`/api/v2/pair/` 与配对裁定冲突、路径绕过）。安全判定一律
**规范化后精确匹配或锚定全匹配**。

### 5.6 Android 侧硬约束
- minSdk 26 / targetSdk 34 / compileSdk 34，AGP 8.7.3 / Gradle 8.9 / Kotlin 2.0.21 / Compose BOM 2024.09.00。

## 7. 会话续聊的裁定（Lead 实测后改写，**优先级高于 §4.2 原文**）

### 7.1 硬墙：桌面端会话不能在网关里续聊（**仅对 headless / SDK 路线成立**）

> **适用范围（本轮收窄）**：本节结论只约束 §7.2 的 headless / SDK profile 路线，**不适用于 §7.4 的桌面端 runtime 通道**。
> 换句话说：不能用 headless/SDK 续聊桌面会话，**但能用桌面端自己续聊**。§4.2 与 §7.3 原表中的
> 「镜像会话一律只读 / 任何 `POST /turns` 都 409」以 §7.4 为准。

headless 实测（隔离 DSH_HOME，真实输出）：

```
cmd : D:\DSH\resources\runtime\cli\bin\dsh.cmd headless --json \
        --session-id session-f8a66cee-3aac-4ef6-9cb4-1e27862e4daa "…"
out : {"type":"error","message":"session \"session-f8a66cee-…\" runs under agent preset
        \"standard\", which the one-shot runner does not compose"}
exit: 1
```

根因：`dsh-headless` 把工具**直接组合在 base 上**，没有 preset realm；而 web/desktop 面把 agent plane
移到 preset 之后（`dsh-web-app/cordis.patch.yml:430-462` 原文：*"The Web surface disables them here and
lets each session mount a preset instead"*）。这是 DSH 的**有意设计**（防止外部进程借隧道逃逸 preset 约束），
不是 bug，网关侧无法绕过，**也不要尝试绕过**。

### 7.2 SDK profile 续聊（stdio JSON-RPC；本轮起**降级为回退路径**）

> **定位变化**：本节自本轮起不再是电脑端会话的续聊通道（那条走 §7.4）。它仍是
> `source:"phone"`（网关自有任务会话）的驱动方式，也是 §7.4 通道不可用时的**回退**（回退时电脑端会话退回只读）。

`dsh --profile sdk` = 官方 SDK 应用：stdout 上按行分帧的 JSON-RPC 2.0，**一个长驻进程可服务多轮**。

| 方向 | 方法/通知 | 载荷 |
|---|---|---|
| client→server | `initialize` | `{cwd, provider, model, reasoningEffort?, maxTokens?}` |
| client→server | `session/prompt` | `{sessionId, contentBlocks:[{type:'text',text}]}` → `{messageId}` |
| client→server | `shutdown` | `{}`（随后进程 exit 0） |
| server→client | `session.event` | `{sessionId, event}` —— **每个事件都推，不过滤** |
| server→client | `session.status` | `{sessionId, status:'running'\|'idle'}` |
| server→client | `subagent.started` / `subagent.finished` | 见 `dsh-sdk-protocol` |

实测握手与一轮完整往返（`initialize` → `{"serverInfo":{"name":"deepseek-harness-sdk-runtime","version":"0.0.1"}}`；
`session/prompt` → `{messageId}`；随后 `session.status running` → `assistant/message`(text `OK`) →
`turn/end.reason.kind=completed` → `session.status idle`；`shutdown` → exit 0）。

**启动形状（Windows 实测）**——`spawn('*.cmd', {shell:false})` 在 Node 24 上直接 `EINVAL`：

```
exe : D:\DSH\DeepSeek Harness.exe
args: --expose-internals <asar>\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\cli.js --profile sdk
env : ELECTRON_RUN_AS_NODE=1, DSH_HOME=<gateway 自己的 home>
cwd : <目标工作区>
```

**SSE 映射**：`session.status→running` ⇒ `turn.started`；`session.event` 中 `user/message`/`assistant/message`/
`tool/call`/`tool/result` ⇒ `message.delta`/`tool.call`/`tool.result`；`turn/end` + `session.status→idle` ⇒ `turn.ended`。
一个进程服务一个 `sessionId`，按需常驻，**不要每轮重启**。

### 7.3 两类会话严格分离（**必做**；「谁驱动 / 能否写」两行以 §7.4 为准）

SDK 会话 header 里**没有 `agentPreset`**（基面 agent），实测：
`{"type":"session","version":4,"id":"sdk-probe-0001","createdAt":…,"cwd":"…","isSeeded":false,"delegationDepth":0}`。

| 维度 | 镜像的 PC 会话 | 网关自己的任务会话 |
|---|---|---|
| 数据源 | `%USERPROFILE%\.dsh\sessions`（**只读**，绝不写入） | 网关自己的 `DSH_HOME`（默认 `~/.dsh-remote/dsh-home`，可配置） |
| 驱动方 | **桌面端 runtime**（§7.4；自本轮起网关可经它提交轮次） | 网关（SDK profile 子进程） |
| 手机可写 | **是** —— 经 §7.4 通道提交，由电脑端 runtime 执行；仅在该会话**正被占用**时 `409 session_busy` | 是（须有活着的运行时） |
| `live` 语义 | 桌面端在跑（原 §7.4，现为 §5.4；更准的信号见 §7.4 的 `session/list.running`） | 网关自有轮次占用表 |
| 列表呈现 | 「电脑上的会话」 | 「手机任务」 |
| **数据源仍然严格分离** | 网关**绝不**往 `%USERPROFILE%\.dsh` 写会话文件 | 网关**绝不**把 SDK 会话写进镜像根 |

### 7.4 桌面端 runtime API 通道（**新通道，已实测跑通**）

> **一句话**：不再另起一个 DSH 进程去"接管"电脑端会话，而是**让电脑端自己的 runtime 执行**这一轮，
> 网关只做提交与订阅。§7.1 的 preset 硬墙因此绕开 —— 不需要绕过它，因为执行者就是原来那个 runtime。

**为什么成立**：桌面 runtime 的会话控制器以 preset 运行时组合的方式恢复既存会话
（`dsh-api-session-controller/lib/index.js:253-275` `ensureSession()` + `:358-371` `composeAgent(presetId)`）；
preset 是**运行时组合**而非持久化身份（`dsh-agent-preset-registry` 读 `agentPreset` 投影而非 header）。
所以"带 `standard` preset 的既存会话"在 headless/SDK 侧组不出来（§7.1），在桌面侧却是它的**原生恢复路径**。

**`session/fork` 的确切语义（`atSeq` 参数）**：`{sessionId, atSeq?}` 在 `atSeq` 处**分出**一个新会话；
它**不是**"续聊原会话"的原语。本通道用它做的实测是：fork 出新会话 → 在新会话上 `session/prompt`（见下），
于是**原会话不变**、新会话被真实驱动 —— 这正是"手机写的消息由电脑端 runtime 真实执行"的证明。

**鉴权**（未公开协议，务必按此实现，不要自创）：

| 项 | 值 |
|---|---|
| 凭据来源 | `%USERPROFILE%\.dsh\.credentials.yaml` 的 `records: client-connection/browser-session.payload.secret`（base64url 编码的 32 字节） |
| cookie 名 | `dsh-auth-<base64url(sha256(authority))>`；`authority` = `127.0.0.1:<port>` |
| cookie 值 | `v1.<base64url(JSON{version:1,authority,issuedAt,expiresAt})>.<base64url(HMAC-SHA256(secretBytes, body))>`，`body` = 上面那段 JSON 的**原字节** |
| 必需请求头 | `Host` 必须是回环（`127.0.0.1:<port>`） |
| 结论 | 能读到该文件的**本机用户**即可驱动桌面端；网关与桌面端**同机同用户**，不引入新的信任边界（§5.5 红线不变） |

**线格式**：

单次调用：

```
POST http://127.0.0.1:<port>/api/<namespace>/<method>
content-type: application/json
{ "type": "client-request", "rpcId": "<uuid>", "method": "<ns>/<method>", "payload": { "args": { … } } }

→ { "result": { "ok": true,  "value": … } }
→ { "result": { "ok": false, "error": { "code": …, "message": … } } }
```

**`args` 的字段名必须与形参名逐字一致**（例如 `session/list` 的形参是 `_request`，就写 `{"args":{"_request":…}}`）。

流式：`ws://127.0.0.1:<port>/api/remote.mux`，一条连接承载多流，靠 `streamId` 区分：

```
client → { "type": "open", "streamId": "<id>", "endpoint": "<ns>/<method>", "payload": { … } }
server → { "type": "item", "streamId": "<id>", "value": … }
server → { "type": "end",  "streamId": "<id>" }
server → { "type": "error","streamId": "<id>", "error": { "code": …, "message": … } }
```

**方法表（本轮用到的）**：

| 方法 | 形参 | 用途 |
|---|---|---|
| `session/list` | `_request` | 电脑端会话清单，含 `running` / `agentAvailable` / `cwd` 与完整投影 |
| `session/projections` | `_request` | 投影数据（标题、统计） |
| `session/page` | `{address:{kind:'session',sessionId}, throughSeq, maxMessages}` | 取既存历史（transcript 分页的另一实现路径） |
| `session/create` | `{workspaceId?, cwd?, sessionId?, agentPreset?}` | 新建会话 |
| `session/fork` | `{sessionId, atSeq?}` | 在 `atSeq` 处**分出**新会话（见上） |
| `session/prompt` | `{requestId, sessionId, mode:'queue'\|'steer', content:[{type:'text',text} \| {type:'image',mediaType,data,name?}]}` | 提交一轮（图片见下） |
| `session/cancel` | `{sessionId}` | 中止当前轮 |
| `session/follow` | 流式，`{address, assistantStream, maxMessages?}` | 订阅该会话的实时事件 |
| `workspace/{create,rename,delete,archiveSession,insertBefore,insertSessionBefore,pinSession}` | — | 工作区与侧栏操作 |
| `workspace/follow` | 流式 | 订阅工作区变化 |
| `directoryPicker/{pick,list,createDirectory}` | — | 目录选择（手机端工作区选择可复用） |

> **`session/prompt` 的图片块（本通道的权威形状，实测得出）**：
> `content` 是 `PromptContentPart[]`，图片块为 `{type:'image', mediaType, data, name?}`，其中
> `mediaType ∈ {'image/png','image/jpeg','image/webp','image/gif'}`（`:1808`）、
> `data` 是**内联 base64**（`:1519-1520` 的 `@Remote('prompt')`，`:2236-2237` 的 `SessionPromptRequest`）。
> **不需要**预先落盘、**不需要** `attachmentId` —— runtime 收到后自己写进
> `$DSH_HOME/attachments/v1/objects/<sha256 前 2 位>/<sha256>`（商店为此按 `sha256` 内容寻址）。
> 本通道的 `session/attachment`（`{sessionId, attachmentId}` → `SessionAttachmentValue`）是**读回**已有图片、
> **不是上传**；host 的 `@Remote` 清单里没有任何 upload/save 方法，所以"手机端发图"只能走本通道的内联 base64。
> 上限（`dsh-attachment-local/lib/index.js:256-291`）：单图 5 MiB、单条消息 20 张、单条消息合计 100 MiB、单像素 4000 万；
> 解码后还要求嗅探出的类型与 `mediaType` 一致（`IMAGE_TYPE_MISMATCH`），错误码全集见
> `dsh-attachment/lib/index.js:4-13`。**手机端的瓶颈不是这些，而是网关/中继的 1 MiB 请求体**（见 §4.3 的 `content` 约束）。

**实测证据（本轮，真实输出）**：`session/list` 返回 **82 个会话**（含 `running`/`agentAvailable`/`cwd` 与完整投影）；
对 `session-c6116e3f-6f3a-479b-bd34-5d9f13d79007`（`seq=276`）`session/fork` → 新会话
`session-b64b78d8-5490-4d8c-936a-09a82c4c9616` → `session/prompt` → `{"accepted":true}` →
`running=true`，`seq` `287→288→291`，`sessionStats` 由 `{turns:2,steps:38,decodeTokens:60236}` 变为
`{turns:3,steps:39,decodeTokens:60408}`；WS 流式订阅实时收到 **29 个事件**直到 `turn/end`。
**这条链证明了"提交真的被执行 + 事件真的能实时回流"，而不是"网关自己写了一份历史"。**

**落到 §4.2 的映射**：

| 面向手机的字段/行为 | 来源 |
|---|---|
| `source:"computer"` 的 `writable` | 电脑端 runtime 可寻址（可枚举到该会话）且未被占用 |
| `live` | `session/list` 的 `running`（比 §5.4 的 mtime 判据更准） |

| `POST /abort` | `session/cancel` |

**已知限制（必须如实转述，不要写成"已完全解决"）**：

1. **Windows 无 flock** → `SessionAlreadyOwnedError`（`dsh-api-session-controller/lib/index.js:241`）不会生效，
   互斥只能靠 `session/list` 的 `running`/`agentAvailable` **加网关侧租赁**（§5.4 的内存占用表同样要生效）。
   即：**并发保护是"尽力而为"**，两个写入者同时抢同一会话时可能各自都成功。
2. 该通道等价于「**手机持有这台 PC 上 DSH 的完整执行能力**」。用户已明确批准手机端权限与电脑端相同，
   **不设降权档位**；这就是 §5.5 红线之外新增的攻击面，因此该通道**只允许回环**，且只在本机用户可读凭据的前提下成立。
3. **依赖 DSH 未公开线协议**，DSH 升级可能变更（方法名、形参名、cookie 方案都可能动）。
   因此必须集中在**单一适配层** `tools/dsh-remote/lib/desktop-api.mjs`：探测失败/调用失败/协议不符时
   一律**回退到 §7.2 的 SDK 路线**（回退后电脑端会话退回只读，`writable:false`），
   **不得**让新通道的故障影响 `source:"phone"` 的既有能力。
4. **适配层落地状态（2026-10-14 复核源码）**：`tools/dsh-remote/lib/desktop-api.mjs` **已存在（621 行）并已接线**
   到 `sessions`（列表/详情）/`turns`/`abort`/SSE 四处，不再"待验证"；细节与逐条覆盖情况见本节末的对齐状态表。
   **仍未验证**的是 **DSH 版本兼容性**：本契约依据的本机 DSH 版本见 §8，升级后方法名/形参名/cookie 方案是否变动
   由实现方在升级时补证。

### 7.5 `driver` 字段与「谁驱动」的判定（**新增**）

| 判定顺序 | 条件 | `driver` | `writable` |
|---|---|---|---|
| 1 | `source:"computer"`（电脑端真实会话） | `"desktop"` | `true`（由桌面端 runtime 执行）；新通道不可用时 `false`（退回只读镜像） |
| 2 | `source:"phone"`（网关自有会话） | `"gateway"` | 见 §4.2 手机可写性（有活运行时才 `true`） |
| 3 | `driver` 字段缺失（旧网关） | 由 `source` **推导**：`computer`→`desktop`、`phone`→`gateway` | **老网关的语义原样保留**：`computer`→`false`、`phone`→按原 `writable` |

- 客户端**不得**因为 `driver` 缺失而拒渲染或报错；`driver` 只用于呈现（例如「由电脑端驱动 / 由手机任务驱动」）。
- 服务端**必须**始终显式返回 `driver`（新增字段）；仅当对端是老网关时才由客户端推导。
- `source` 与 `driver` **不可互相推导出可写性**：可写性以 `writable` 字段为准（§4.2）。
- **数据源不与驱动方绑定**：`source:"computer"` 的会话**永远**读自 `%USERPROFILE%\.dsh`（网关只读镜像），
  「可写」指的是"能提交轮次、由电脑端 runtime 落盘"，**不是**"网关直接写镜像根"（§7.3）。

**本轮实测发现并修掉的两个缺陷（登记，勿回归）**：

1. **详情的 `live` 必须以桌面端运行态为准**。此前详情只用文件 mtime 判据（§5.4 的 60s 窗口），刚跑完一轮的
   60 秒内会误报 `live:true`，手机端会一直显示"电脑端正在驱动"；现在列表与详情用**同一个真值源**
   （`session/list` 的 `running`），收束后 `live:false`。**同一个会话在列表与详情里不得给出互相矛盾的 `live`。**
2. **重复投递**：观望型 `session/follow` 与网关轮次通道曾同时产帧，一轮出现 **3 个** `turn.started`；
   现已收敛为 **2 个**（桌面端真实事件 + 网关回执），`turn.ended` **唯一**。
   客户端**不得**把 `turn.started` 的条数当作轮次计数。

> 其余已按契约落地：电脑端会话 `writable = desktop !== null && !isSubagent`（`http.mjs:907-908`，subagent 仍只读，
> 关闭开关时为 `desktop_disabled`）、`live` 用 `session/list` 的 `running` 覆盖 mtime 判据（`http.mjs:915-925`）、
> 轮次经 `session/prompt` 提交并带 `driver` 回执（`session-runner.mjs:848`）、SSE 帧带 `source:"computer"`。
> 自动化测试**尚未覆盖** `driver` 字段（`tools/dsh-remote/test/v2.test.mjs` 内无 `driver` 断言）。

### 7.6 手机新建任务落在电脑端（`host` 与 `createdBy`；**本轮新增，已端到端实测**）

§7.4/§7.5 解决的是「手机**接着聊**电脑上**已存在**的会话」；本节解决「手机**新建**的任务**建在电脑端**」。
两者合起来才是双向：**电脑接手机的活，手机接电脑的会话**。

**不是接力，不是复制历史**：会话是**原生**建在电脑端 DSH 的 home 与工作区里的，电脑端打开就是同一个会话。

#### 7.6.1 三字段各说各的事（客户端**不得**互相反推）

| 字段 | 回答的问题 | 取值 | 手机新建 + 落电脑端时的值 |
|---|---|---|---|
| `createdBy` | 谁**发起** | `"phone"` \| `"desktop"` | `"phone"` |
| `source` | 数据**长在谁家**（§4.2） | `"phone"` \| `"computer"` | `"computer"` |
| `driver` | **现在**谁在驱动（§7.5） | `"gateway"` \| `"desktop"` | `"desktop"` |

为什么必须新增 `createdBy`：落电脑端后 `source` 必然是 `"computer"`，手机端**再也无法**靠 `source === 'phone'`
认出「这是我发起的」。判定以网关自有 `<config.home>/phone-sessions.json` 的登记为准（登记过 → `"phone"`，否则
`"desktop"`）。**缺失 `createdBy` 的老网关**下，客户端退回旧行为（`source === 'phone'` 视为手机发起），
**不得**因此拒渲染。

#### 7.6.2 请求字段 `host`（可选）

| 取值 | 行为 | 202 回执 |
|---|---|---|
| 缺省 | 桌面端通道可用 → 落电脑端；**未接入 → 落网关自有 home**（向后兼容） | 见下两行 |
| `"desktop"` | 在电脑端 DSH 里新建会话（**必须同时给 `workspace`**） | `source:"computer"` + `createdBy:"phone"` + `driver:"desktop"` + `host:"desktop"` + `turnId` + `fromSeq` + `workspace` |
| `"gateway"` | 网关自有 `DSH_HOME`（SDK profile 子进程，§7.2） | `source:"phone"` + `createdBy:"phone"` + `driver:"gateway"` + `host:"gateway"` + `turnId` + `fromSeq` + `access` |

三类错误（**逐字**，与 §4.2 的错误表一致）：

| 场景 | 状态码 / `code` | `message`（逐字） |
|---|---|---|
| `host` 取值非法 | `400` `bad_request` | `host 只能是 desktop 或 gateway` |
| `host:"desktop"` 但缺 `workspace` | `400` `bad_request` | `在电脑端新建任务必须指定 workspace（电脑端是按工作区登记会话的）` |
| `host:"desktop"` 但网关未接桌面端 | `503` `desktop_unavailable` | `网关未接入桌面端 DSH runtime，无法在电脑端建会话；请改传 host:"gateway"，或先启动电脑端 DSH` |
| 建会话失败 | `502`（`code` 透传） | 前缀 `在电脑端创建会话失败：` + 原因 |
| 会话**已建**、首轮投递失败 | `502`（`code` 透传） | `会话已在电脑端建立（sessionId=…），但首轮投递失败：…` |

> 最后两行的区别是**语义级**的：末一种情况下会话**已经真实存在于电脑端**（也已登记进 `phone-sessions.json`），
> 客户端不得把它渲染成"创建失败、什么都没发生"。

同一个请求体还有三个**可选**的模型字段 `provider` / `model` / `reasoningEffort`（v2.10.0 新增）：
它们决定「这个会话用哪个模型」，两条通道各自的生效方式与失败降级见 **§7.8**。

#### 7.6.3 落电脑端的实现形状（**勿实现成"复制会话"**）

调用顺序：`workspace/create {path}`（幂等，拿 `workspaceId`）→ `session/create {workspaceId}`（§7.4）
→ 登记 `<config.home>/phone-sessions.json` → `session/prompt`。

- **`session/create` 必须走 `workspaceId`、不能走 `cwd`**：实测走 `cwd` 建的会话**不登记进任何工作区**，
  随后 `workspace/insertSessionBefore` 报 `workspace/move-invalid … the session is not accounted`。
- **网关绝不写 DSH 自己的会话文件**（`session.v4.jsonl.zstd` 的 header 是 DSH 的格式）：塞网关私有字段会污染
  用户真实 home，且随 DSH 版本变化失效；用网关自己的 `phone-sessions.json` 对 DSH 侧完全无感。
- 索引形状 `{version:1, sessions:{<sessionId>:{createdAt, host, workspace, access, title}}}`，`MAX_ENTRIES=500`，
  **损坏/缺失/版本不认识 → 按空索引继续**（宁可丢"我发起"标记，也不能让网关起不来）。
- `ERROR_STATUS` 新增：`desktop_unreachable:503`、`desktop_unavailable:503`、`desktop_disabled:503`、
  `desktop_unauthorized:502`、`desktop_error:502`。

#### 7.6.4 两条实测限制（U15 / U16；**手机端必须如实呈现**）

1. **（U15）电脑端会话的 `access` 权限档手机端无法指定**：`dsh-web-app/presets/standard.patch.yml` 里没有任何
   permission/approval/sandbox 配置，权限来自**桌面端 DSH 进程自己的** `DSH_PERMISSION_MODE`（全局、非每会话）。
   因此 `host:"desktop"` 时 `access` **不生效**；只有 `host:"gateway"`（SDK 子进程）通道能按任务指定档位。
   客户端**不得**把它渲染成"已按你选的档位执行"。
2. **（U16：原状如此，v2.6.0 起已可应答 → 见 §7.7）** 原状：电脑端会话在 `approval/policy: ask` 下触发审批时
   手机端无法应答 —— `dsh-api-session-controller` 的 Remote 方法表里**没有任何**批准/拒绝审批的方法，
   该轮会**挂住**直到有人在电脑端 UI 批准。客户端**不得**把它渲染成"无限转圈"，应提示回电脑端处理。
   **v2.6.0 的解法不是新增 Remote 方法**，而是接上电脑端 runtime 已有的**可应答 waterfall 事件流**（§7.7）；
   上面"不得渲染成无限转圈"的要求**依然有效**，因为 TTL 到期后电脑端那一轮**仍在等待**（§7.7.7 限制 2）。

#### 7.6.5 端到端实测证据（2026-10-14，网关 `2.1.0`）

最新一次 `===== 结果：PASS =====`：marker **`e2e-task-final`**（**19 项断言**；当次 19 项，冻结版探针恒为 29 项 —— 见
[验收报告 §13](../04-验收/验收报告.md)「两套 marker 的关系」）；同探针的早期跑为
`e2e-task-first`/`e2e-task-wsfix`（后者是修掉 D-06 后的复跑）。
要点：`POST /api/v2/tasks` 不带 `host` → `202` 且 `source`/`createdBy`/`driver` 三字段齐（`computer`/`phone`/`desktop`）；
`workspace/create` 回读 `sessionIds` **含该会话** —— 这是"电脑端能接手"的**唯一**判据（不是"文件写在同一个目录"）；
首轮在电脑端跑完 `asOfSeq 15 → 20`、`live:false`、`turns=1`、用时 **2.7 s**；transcript 含 prompt 原文与助手回复
「收到」（证明对话真的落在电脑端那条会话上）；列表命中
`{source:"computer", createdBy:"phone", driver:"desktop", writable:true}`；`host:"gateway"` 仍走 SDK 通道，
其 abort 是**破坏性**的（`resumable:false`），与电脑端通道的 `resumable:true` 形成对照。

#### 7.6.6 回退与边界

- `desktop.enabled=false` 或桌面端未运行时：带 `host:"desktop"` 的请求得到 `503 desktop_unavailable`；
  **不带 `host`** 的请求自动落回 `source:"phone"`（网关自有 home），既有能力不受影响。
- 本节只新增**请求字段** `host` 与**响应字段** `createdBy`，属 §4.5 的纯新增，`X-Api-Version` **不递增**（仍为 `2`）。
- 适配层仍是**唯一**改动点：`tools/dsh-remote/lib/desktop-api.mjs`（§7.4 限制 3）。

### 7.7 审批与提问（可应答 waterfall，v2.6.0 新增）

> 本轮新增的能力：手机可以直接**应答**电脑端会话弹出的**审批**（`approval/request`）与**提问**
> （`user-questions/request`）。实现上**不是**新增 Remote 方法，而是复用电脑端 runtime 已有的
> **可应答 waterfall 通道**（§7.7.1）。它**关闭了 §7.6.4 的 U16**，但带来四条必须如实呈现的限制（§7.7.7）。

#### 7.7.1 为什么必须走事件流，而不是 unary RPC

- 会话 RPC 面（`session/*`、`workspace/*`、`agentPresets/*`、`directoryPicker/*`、`workspaceFiles/*`）里
  **没有任何** approve/deny/confirm 方法；`dsh-user-approval` 的 `decide()` 是一条 **Cordis waterfall**：
  `ctx.waterfall(scopeTarget(req.agent, req.agent), 'approval/request', req, () => Promise.resolve('unavailable'))`。
- `dsh-api-remotes/lib/types/remote-events.js` 的 `API_REMOTE_FORWARDED_EVENTS` 共 **27 条**转发事件，
  其中**只有 2 条**是 `mode:'waterfall'`（可应答）：`approval/request` 与 `user-questions/request`；
  其余 25 条都是 `emit`（发出去就完事，没有回执）。
- 结论（决定了本节全部形状）：审批/提问是**"向所有监听者提问"**，不是"可以调用一次的方法"，
  所以**答案必须从提出问题的同一条流回去**。手机端**不经手** `$events`：网关侧的 `ApprovalBridge`
  独占那条订阅并做对账（`tools/dsh-remote/lib/approvals.mjs`）。

#### 7.7.2 线协议：`$events` waterfall 帧 + `$events/result`

| 环节 | 形状 |
|---|---|
| 载体 | WS `/api/remote.mux`，逻辑流 `$events`；`payload.args` **必须是空对象** `{}`（否则 `arguments-invalid`） |
| 首帧 | `{type:'ready', clientId, host:{home}}` —— `clientId` **只能**从这里取，不是客户端自己编的 |
| 提问帧 | `{type:'waterfall', event, eventId, agentId, request}`；`projectRemoteEventRequest` 已剥掉 `agent`/`signal` |
| 应答 | `POST /api/$events/result`，体 `{clientId, eventId, outcome}`；`outcome` ∈ `{kind:'next'}` / `{kind:'result', value?}` / `{kind:'rejected', error}` |

- **线上没有 `approvalId`**：`eventId` 是**唯一**可用于对账的键。durable 会话日志里 `approval/decided` 的
  `data.id` 与它**不是**同一个值 —— 客户端不要拿日志里的 id 来提交。
- 提交前 `$events` **必须活着**：网关按 `clientId` 查 `remoteEventClients`，流一断（`openRemoteEvents` 的
  finally → `removeRemoteEventClient`）提交就会得到
  `typert gateway: Remote event result identifies no active event stream`。
  所以桥维持**一条常驻订阅 + 自动重连**，而不是"要答的时候临时连一次"。
- 桥的默认参数：TTL **15 min**（`DEFAULT_APPROVAL_TTL_MS`）、未决表上限 **50**（`DEFAULT_MAX_PENDING`）、
  重连间隔 **2 s**（`DEFAULT_RECONNECT_MS`）、单次流超时 **10 min**（`DEFAULT_STREAM_TIMEOUT_MS`）、
  过期清扫 **30 s**（`sweepMs`）。
- 入表时按 `eventId` **去重**（重连后电脑端会把**仍未决**的帧重放一遍）；`pending` 先写再清扫，
  因此 `maxPending` 是**硬上限**。`sessionId` 一律取帧上的 `agentId` —— 实测电脑端的 `agentId`
  **就是会话 id**（形如 `session-<uuid>`）。
- 桌面端报 `no active event stream` 时，桥**立刻**把 `connected=false`/`clientId=null` 强制重连，
  而不是拿同一个 `clientId` 死循环重试。

#### 7.7.3 HTTP 端点（两个，形状与 `tasks` 对齐）

| 方法 | 路径 | 成功响应 | 说明 |
|---|---|---|---|
| `GET` | `/api/v2/approvals`（可选查询参数 `?sessionId=<id>`，**按会话过滤，v2.6.0 修复后已生效**） | `200 {ok:true, approvals:[PublicApproval…], state}` | 未决列表，**最新在前**；不带参数＝全部未决，未知会话＝**空数组**（判据见 §7.7.7）。`state` 见 §7.7.6。给冷启动/刚重连的手机用，不必等一次事件往返 |
| `POST` | `/api/v2/approvals/{eventId}` | `200 {ok:true, event, outcome}` | 提交答案；路径参数是 **`eventId`**（不是 `approvalId`） |

- 两个端点都**不在** `PUBLIC_ROUTES`：开了 `config.authRequired` 就必须带 Bearer（否则 `401`）；
  也不在 `LOOPBACK_ONLY_ROUTES`，所以**可以经中继隧道从手机调用**（这正是它的用途）。
- 方法不对 → `405`（`ROUTE_METHODS` 固定 `approvals:['GET']`、`approvalAnswer:['POST']`）。
- 能力宣告：`health.capabilities` 含 `approvals` 与 `approvals.answer`，顶层 `approvals` = 桥的 `state()` ——
  手机据此判断"这个网关能不能收审批"。

**错误映射（逐字；客户端据此决定"刷新列表"还是"重试提交"）**

| `code` | HTTP | 触发条件 |
|---|---|---|
| `unauthorized` | `401` | 缺/错 Bearer |
| `bad_request` | `400` | `eventId` 为空（`缺少 eventId`）／请求体不是 JSON 对象（`请求体必须是 JSON 对象`）／答案形状非法（§7.7.5） |
| `not_found` | `404` | 该 `eventId` **从未来过**、**已经答过**、或**已过期被清扫**（三种原因共用同一码） |
| `approval_expired` | `409` | 已过 TTL。**故意不复用 `not_found`**：它既不是"没有这一项"也不是并发冲突，混用会让手机把"刷新列表"错做成"重试提交" |
| `desktop_unavailable` | `503` | 桥不可用 / 事件流未连接 / `clientId` 为空；文案 `与桌面端的事件流未连接，暂不能提交答案（电脑端那轮仍在等待）`。响应**仍带 `event`**，手机可继续渲染那张卡 |
| `desktop_unreachable` | `503` | 调桌面端抛错（`err.code` 透传） |
| `desktop_unauthorized` | `502` | 桌面端凭据被拒 |
| `desktop_error` | `502` | 其余（含桌面端透传的 `gateway/*`）—— 属**通道**问题，不是请求问题 |

- **校验顺序有语义**：`answer()` 先查未决表 → 再判 TTL → **再校验请求体** → 最后才看通道状态。
  理由：若先把"通道断"报成 `503`，手机在重连窗口内会**重试一个永远不可能成功的请求**；
  现在畸形请求无论通道通不通都稳定得到 `400`。（自动化用例第 9 条把"未知/非法/未连接"三种失败钉成三个不同的码。）

#### 7.7.4 `PublicApproval`（未决项与 `approval.asked` 的负载，**恰好 9 个字段**）

| 字段 | 类型 | 含义 |
|---|---|---|
| `eventId` | `string` | 唯一对账键（提交答案就用它） |
| `sessionId` | `string` | 会话 id（= 帧上的 `agentId`） |
| `kind` | `"approval"` \| `"question"` | 两类共用同一条通道 |
| `toolName` | `string` \| `null` | 审批：帧上 `request.toolName`；提问：**恒为** `"ask_user_question"` |
| `callId` | `string` \| `null` | 审批取顶层 `req.callId`；提问取 `request.wait.callId` |
| `reason` | `string` \| `null` | 审批的理由（提问为 `null`） |
| `questions` | `Question[]` \| `null` | 仅 `kind:"question"` 有内容 |
| `at` | `number` | 网关收到该帧的毫秒时间戳 |
| `expiresAt` | `number` | 网关侧 TTL 到期时刻（**只是记账**，见 §7.7.7 限制 2） |

网关**刻意不下发** `agentId` 与内部字段（如 `displayReason`、`intent`），手机端不要假设能拿到。
（`publicEntry()` 的键就上表 9 个；历史用例标题写作"8 个字段"是笔误，以本表为准。）

#### 7.7.5 提问的形状与答案校验

`questions[]` 每项（`normalizeQuestions` 只做**形状收窄**：丢未知字段、缺省补 `null`、过滤非对象项）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `string` | 回填答案时用它对应 |
| `question` | `string` | 题干（缺失为空串） |
| `header` | `string` \| `null` | 分组/标题 |
| `detail` | `string` \| `null` | 补充说明 |
| `options` | `[{label, description\|null}]` | **没有 `options` = 自由文本题**（只能填 `custom`） |
| `multiSelect` | `boolean` | `true` 才多选。**单选时桌面端整个键都缺席**（不是 `false`）——归一后手机端永远看到布尔值，不会遇到 `undefined` |

答案体（`POST` 的 body）三种形态：

| 场景 | 体 | 说明 |
|---|---|---|
| 弃权 | `{"abstain":true}` | 翻成 `{kind:'next'}`：waterfall 放行，交给下一个应答者；**没人答时上游归一为 `unavailable`（＝拒绝）** |
| 审批 | `{"outcome":"allowed-once"\|"rejected"\|"cancelled"\|"unavailable"}` | 只有这 4 个取值合法 |
| 提问 | `{"answers":[{"id":"q1","selected":["…"],"custom":"…"}]}` | `custom` 可省；`answers` 必须**非空数组**，每项 `id` 必须是非空字符串 |

**逐条红线**（写错就是"点了没反应"或静默变形）：

- `selected` **必须是数组**：裸字符串会被**硬拒** —— 工具侧做 `[...answer.selected]`，
  `"blue"` 会静默变成 `["b","l","u","e"]`。
- `selected: []` 合法 = **跳过该题**；`selected` 与 `custom` **同时缺失** → `400`（残缺请求）。
- 自由文本字段名是 **`custom`**，不是 `text`：桌面端 `answerSchema` 是 `.strict()`/`additionalProperties:false`，
  只认 `id`/`selected`/`custom` 三个键 —— 多写一个键会让**整份提交**校验失败，用户看到的是"按了没反应"。
- 工具入参拼 `multi_select`，但**转发帧上是 `multiSelect`**：只有后者在线上。
- `intent`（`{kind, approve}`）**不下发**：它只提示哪个 label 算"同意"，不改变可答性。

#### 7.7.6 SSE 事件（挂在既有会话流上）

三个事件经**既有**的按会话事件流下发（`/api/v2/sessions/stream`），**每个都带 `sessionId`** ——
否则按会话订阅的手机收不到；类型名与既有风格一致。

| 事件 | 负载 |
|---|---|
| `approval.asked` | §7.7.4 的 9 字段 `PublicApproval` |
| `approval.decided` | `{eventId, sessionId, kind, decision, by:'phone', at}`（`decision` 是 4 个审批结论之一） |
| `approval.expired` | `{eventId, sessionId, kind, reason, at}`，`reason` ∈ `"expired"` \| `"answered-too-late"` \| `"dropped"` |

`state()` 形状（`GET` 列表响应里的 `state` 与 `health.approvals` 共用）：
`{available, connected, pending, startedAt, reconnects, lastError, counters:{asked, approved, rejected, expired, answered, failed}}`。
`stop()` 清空未决表**但不作答**（不留永不返回的循环）；`available` = 网关是否接入了桌面端。

#### 7.7.7 四条如实限制（手机端必须照此呈现）

1. **没有重放保证：订阅必须先于提问。** 电脑端只把 `pendingRemoteEvents` 里**仍未决**的事件重放给新客户端，
   已经决定的**不补**。手机端**不能**"事后"看到刚错过的审批 —— 正确姿势是**保持订阅**，断线重连后仍未决的
   会自己回来；列表端点只是**兜底**，不是重放。
2. **没有超时：TTL 只是网关侧记账。** 15 分钟到期后手机不能再答（`409 approval_expired`），但**电脑端那一轮
   仍然挂着**：工具调用不返回、`turn` 不结束。手机端**不得**渲染成"已自动拒绝/已超时处理"。
   （唯一例外：`ask_user_question` 的**超时变体**到点会以 `{pending:true, callId}` 让该轮继续跑，
   迟到的答案会作为一条 `source.kind='user-question-reply'` 的用户消息进入会话 —— 迟到 ≠ 不可答。）
3. **先到先得，没有"总是允许"。** 电脑端 UI 自己也是一个 `$events` 客户端：**第一个**答案生效，
   后到的答案**既没有错误、也无法改变结果**；`ok:true` 只表示网关**收下了**这次提交。
   手机端必须假设"可能已经有人在电脑上答过了"；列表刷新后该项消失**不等于**"我答成功了"。
4. **只覆盖活在电脑端 runtime 里的会话**（`source:"computer"`，含手机新建、`host:"desktop"` 的会话）。
   网关**自己**用 `dsh --profile sdk` 起的会话不在那条进程里，它们的审批**永远不会**出现在这条流上 ——
   手机端不能因为"列表是空的"就断言"这个会话没有待审批"。

**实现现状与额外注意（如实登记，勿当契约承诺）**

- `GET /api/v2/approvals?sessionId=<id>` 的**按会话过滤已生效**（v2.6.0 修复）：dispatch 现在把 **URL** 传下去
  （`case 'approvals': return onListApprovals(res, url)`），`onListApprovals` 用
  `url.searchParams.get('sessionId') || null` 取值 —— 必须这样读的原因是 `routeOf()` **只吃 pathname**，
  路由对象里从来没有 `sessionId`（修复前恒返回**全部**未决项，客户端以为的"按会话隔离"是假的）。
  契约行为：不带参数＝全部未决；`?sessionId=<id>` ＝只回该会话；未知会话＝**空数组**。
  永久证据＝`test/approvals.test.mjs` 的 `HTTP：?sessionId= 过滤真的生效（两条未决分属两个会话）`
  （同时推 `session-a`/`session-b` 两条未决帧，断言不带参数 2 条、各自 1 条、未知会话 0 条 ——
  旧用例只推 1 条，"过滤生效"与"压根没过滤"输出完全相同，**不可证伪**）。
- `$events` 会转发**所有**会话的 waterfall 帧（谁订阅谁就能看到别人的审批）。若手机端自行订阅，
  必须按 `frame.agentId === sessionId` 过滤，否则会**替别的会话作答**；弃权用 `{kind:'next'}`。
- 电脑端的**策略**仍可能让审批根本不发生：`policy:"never"`（如 `danger-full-access`）在派发前就短路成
  `rejected`，不会进 waterfall；而审批**只**由沙箱升级路径产生（工具调用带 `sandbox_permissions` + `justification`），
  没有任何 Remote 方法能"自己造一个审批"。这条流解决的是"**已经**弹出来的问"。
- 本节只**新增**端点与事件类型，属 §4.5 的纯新增：`X-Api-Version` **不递增**（仍为 `2`）。

### 7.8 每任务模型选择（`provider` / `model` / `reasoningEffort`，v2.10.0）

与 §7.6.2 的 `host` **同一个请求体**（`POST /api/v2/tasks`）新增三个**可选**字段。
v1（`POST /api/v1/tasks`）**一字不改**：headless profile 只接受「任务文本」一个位置参数，
v1 的 `model`/`reasoningEffort` 至今只记录不转发（`tools/dsh-remote/README.md` §7 第 1 条）。

| 字段 | 一旦出现的要求 | 缺省 | 生效方式 |
|---|---|---|---|
| `provider` | 非空字符串 | `null` | 电脑端 `session/selectModel`；网关路径经 SDK `initialize` 下发 |
| `model` | 字符串（历史口径：非字符串＝没传；空白＝没传） | `null` | 同上 |
| `reasoningEffort` | 非空字符串 | `null` | 同上 |

**六条铁律**：

1. **顺序（落电脑端）**：`workspace/create` → `session/create` → **`/permission <preset>`（v2.11.0，只有显式传 `access` 时）**
   → **`session/selectModel`** → `session/prompt`。
   模型与权限都必须**早于首轮投递**：桌面端会话的模型是「下一次组合 agent 时生效」，而首轮投递**就**触发组合；
   顺序反了这一整轮会跑在用户没选的模型/旧权限上。
2. **切模型失败不判任务死**：会话**已经真实存在于电脑端**（也已登记进 `phone-sessions.json`），
   于是失败降级成响应字段 `modelApplied:false` + `modelWarning:"<原因>"`，任务**照常投递**、`202` 照常返回。
   手机端必须如实呈现 `modelWarning`，**不得**渲染成"创建失败、什么都没发生"。
3. **`modelApplied` 只在请求带了 `model` 时出现**：`true`＝已切上；`false`＝降级（必配 `modelWarning`）。
   **字段缺失＝未知**（老网关），客户端不得当成 `false` 渲染成"没切上"。
4. **只传 `model`、不传 `provider` 是合法的**：`session/selectModel` 的 `provider` **必填**，
   网关先从 `GET /api/v2/models`（§4.7）反查。反查**只推断 provider，绝不改 `model`**（不得编造 model id），
   三个分支（2026-10-16 裁定，取代此前"多命中一律不猜"的绝对口径）：
   - **唯一命中**（恰好一个分组提供这个 id）→ 用那个分组 id；
   - **多命中**（同一个 id 经多个 provider 路由；**实测** `deepseek-flash` 同时在 `deepseek-official`
     与 `deepseek-account` 下）→ 用目录的**默认 provider**：用户选的是"模型"而不是"账号"，这些 id 指向
     同一个模型，属可接受的推断；为此回 `4xx` 会打断一个合法场景，且失败对用户毫无解释力；
   - **零命中**（目录里没有这个 id，即桌面端当前没把它列为可路由）→ **不拿默认 provider 顶替**（那等于
     用另一个模型冒充用户选的模型）：跳过 `session/selectModel`，如实回 `modelApplied:false` +
     `modelWarning:"桌面端模型目录里没有 <model>，无法确定 provider；未切换模型"`，任务**照常投递**。

   三个分支都**不返回 4xx**：模型名本身可能合法，只是当前路由不到它。
5. **畸形字段＝`400 bad_request`**（不静默忽略）：`provider`/`reasoningEffort` 出现但不是非空字符串即
   `400`，`message` 逐字为 `<字段名> 必须是非空字符串`（如 `provider 必须是非空字符串`）。
   静默降级成"没选模型"会让界面显示着 A provider、实际跑的是网关默认 —— 正是本轮要消灭的
   「模型选择被悄悄丢掉」。`model` 保持历史口径，不在此列。
6. **模型是「每会话/每进程」的，不是「每轮」的**（网关路径）：`dsh --profile sdk` 的模型只能经
   `initialize` 握手下发，而一个子进程只握手一次。因此**首次**为会话建运行时用任务里的模型
   （缺省回落 `dsh.provider`/`dsh.model`/`dsh.reasoningEffort`），**同一会话后续轮次新传的模型被有意忽略** ——
   中途换模型要杀掉正在跑的轮次（进程里可能有未落盘的工具调用与上下文），把"跑完这一轮"换成"换模型"
   是错的默认值。要换模型就**新建任务/新会话**；手机端不要把"这一轮传了 `model`"渲染成"这一轮换了模型"。

`GET /api/v2/health` 的 `capabilities` 新增 `models` 与 `task.model`（§4.5 纯新增，`X-Api-Version` 不递增）。
老网关没有这两条：手机端**先问能力再显示模型选择器**，否则 `model` 会被静默丢掉，用户看到的是
「选了，但用的是别的模型」这种最难查的现象。

### 7.9 对话内修改会话权限（v2.11.0）

用户需求原话：「手机端想给全部权限的话只能选择在仅在手机上执行，这样不行，这个权限要在对话的时候可以改」。

#### 7.9.1 读取：`permission` 视图

`GET /api/v2/sessions`（每项）与 `GET /api/v2/sessions/{id}`（顶层）新增：

```json
"permission": {
  "currentValue": "workspace-write",
  "options": [
    { "value": "read-only", "name": "Read Only", "description": "…", "selectable": true },
    { "value": "workspace-write", "name": "Workspace Write", "description": "…", "selectable": true },
    { "value": "danger-full-access", "name": "Full Access", "description": "…", "selectable": true }
  ],
  "editable": true,
  "source": "desktop",
  "reason": null
}
```

- 电脑端会话：`currentValue` 来自桌面端 `session/projections.values.permissions.currentValue`；
  `editable` = 该会话可写（电脑端通道可用、非子代理）。即使不可写也**下发当前档位**，界面只禁用入口。
- 网关自有会话（`source:"phone"`）：`currentValue` 由任务创建时的 `access` 推出（`workspace`→
  `workspace-write`，`full`→`danger-full-access`），`editable:false`，`reason:"gateway_access_fixed"`
  （SDK 进程启动时固定，没有运行中 setter）；`options` 只含 `workspace-write` / `danger-full-access`。
- 字段缺失（旧网关 / 桌面端离线）：客户端显示「权限未知」，**不得**拿 `workspace-write` 当默认值
  —— 用户可能早就在电脑端开了全部权限，报错档位比不报更糟。
- `currentValue` 不在固定表内（桌面端自定义 preset）时，`options` 末尾追加一个
  `{value:<当前值>, name:"Custom", selectable:false}`，只展示、不可选。

#### 7.9.2 写入：`POST /api/v2/sessions/{id}/permission`

```json
// 请求
{ "preset": "danger-full-access" }
// 200
{ "ok": true, "sessionId": "session-…", "preset": "danger-full-access",
  "applied": true, "verified": true, "commandId": "cmd-…",
  "permission": { "currentValue": "danger-full-access", "editable": true, "source": "desktop", "options": […] } }
```

实现（**唯一写入路径**）：网关调用桌面端 `commands/execute`
`{agentId:<sessionId>, line:"/permission <preset>", submittedAttachments:[]}`，然后回读
`session/projections` 的 `permissions` 投影核对。桌面端自己的权限选择器走的是同一条命令，
因此手机与电脑看到的是**同一个会话级状态**，不是两套。

- `preset` 只接受 `read-only` / `workspace-write` / `danger-full-access`；其余 → `400 bad_request`。
  桌面端 0.2.0-rc.2 的 `permissions` 投影只回 `currentValue`，所以这三个值是网关的**稳定词表**，
  不从投影的 `options` 推断。
- 只有 `source:"computer"` 且非派生会话可改；`source:"phone"` → `400`（网关自有会话权限创建时固定）。
- 桌面端命令返回 `kind:"error"`（如未知 preset）→ `502`，`message` 原样带命令原因；**绝不**回 200。
- 成功后网关向 `session.updated` 附带同一个 `permission` 视图广播（同一会话的其他手机/页面立即更新）。
- 权限是会话级事实：三个事件（`permission/preset` / `sandbox/mode` / `approval/policy`）写进该会话日志，
  重启后按 replay 恢复；切换只影响**之后**的沙箱/审批判定。
- **全部权限**在手机端必须二次风险确认后再提交（与桌面端 `Full access` 风险门一致）；网关不做二次确认
  （它只负责忠实执行已认证设备的请求）。
- 能力位：`session.permission`（读 + 写）、`workspaces.desktopSync`（§4.3 工作区同步）。
- 新建电脑端任务时 `access` 的落地顺序见 §7.6：`workspace/create` → `session/create` →
  **`/permission <preset>`** → `session/selectModel` → `session/prompt`；权限失败是软失败
  （`permissionApplied:false` + `permissionWarning`，任务照常投递）。

## 8. 实现环境硬约束（实测，三方都要遵守）

1. **Windows + Node 24：`spawn` 一个 `.cmd` 且 `shell:false` → `EINVAL`**；`shell:true` 可用，但**绝不能**让用户
   prompt 经过 shell（含 `& | ^ % "` 的 prompt 会被解释）。正确做法是解析 `dsh.cmd` 拿到
   `DeepSeek Harness.exe` + `cli.js` 后**直接 spawn exe**（见 §7.2）。
2. **`D:\DSH\resources\profile\...\dsh\lib\bin.js` 是旧版 CLI**，`--json`/`--session-id` 都不支持。
   必须从 `dsh.launcher`（`.cmd` 路径）解析出 exe/cli.js/flags，或显式覆盖；v1 既有键行为不得回归。
3. **DSH 会话帧必须结构解析**：帧头恒 6 字节 `28 b5 2f fd 04 58`（FHD=0x04 表示**无 FCS 字段** → 无法从头部
   得知明文长度），只能用 block header 遍历。**截断帧不会抛错**（`cut=1` 返回完整明文、`cut=8/40/200` 返回 0 字节），
   所以必须结构判定；torn tail 抢救用 `finishFlush: 1`（写成 8 会 `ERR_OUT_OF_RANGE`）。
   权威算法见 DSH 自己的 `scanZstdFrames`（`dsh-session-persistence-jsonl/lib/index.js:1300`）。
4. **会话列表数据源**：`%USERPROFILE%\.dsh\storages\workspace.json`（`global.workspaceIds` 权威顺序；
   `tables.workspaces[id].sessionIds` **天然排除 subagent** —— 实测 11 个 session 目录只有 2 个在 sessionIds 内）；
   title/统计/在跑标志读 `storages\session_projcache\sessions\<id>.json`（v6/v7）；
   **忽略** `storages\session_projcache.json`（停更的遗留整单元文件，unit v3、seq 还在 v0 空间）。
   `updatedAt = max(createdAt, sessionListMetadata.lastPromptAt ?? 0)`（只有用户消息推进）。
   projcache 每次写都是「临时文件→fsync→rename」原子替换，**并发读安全**，但滞后 0~9 个事件。
5. **`workspace/changes` 事件只有 `{turn}`** —— 文件清单与增删行数**不落盘**（只活在内存服务里）。
   工作区改动**必须**走 git / 文件系统，不要指望会话日志。
6. **Windows 没有 `session.lock`**（POSIX 才用 flock；Windows 用命名内核信号量，外部读不到）。
   live 判据：projcache `turnBoundary.openTurnStartSeq !== null`（有轮次在跑）、
   `sessionStats.openStep`/`pendingCalls`（有 step/工具在飞）；**文件 size 采样必要不充分**
   （实测 3 个会话 6 秒 0 字节却仍在跑）。「一轮结束」唯一权威信号 = `turn/end`。
7. **`dsh web --port 0 --no-open` 可再起一个完整 Harness**（实测：`http://127.0.0.1:50103/?token=…`），
   不占用桌面端 `19387`。其 Web 壳与 `/api` 都要求 URL 上的 `?token=`（或该 token 派生的 cookie）——
   本轮**不**把它作为主通道（避免依赖未公开 RPC 线格式），仅作为已知备选记录在案。
8. **桌面端 `session/create` 必须走 `workspaceId`，不能走 `cwd`**：实测走 `cwd` 建的会话**不登记进任何工作区**，
   随后 `workspace/insertSessionBefore` 报 `workspace/move-invalid … the session is not accounted`。
   正确顺序：`workspace/create {path}`（幂等，拿 `workspaceId`）→ `session/create {workspaceId}` —— 见 §7.6.3。
9. **桌面端轮次的订阅流必须在收束时显式关闭**：收到 `turn/end` 是**提前 return**，异步生成器仍挂在 WebSocket 上
   （只有 `openStream` 的 `finally` 才会 `socket.close()`），收束路径**必须**补 `await iterator.return?.()`。
   否则**每跑一轮泄漏一个 WebSocket**，未 unref 的 socket 吊住事件循环，网关进程**退不出去**
   （实测：不加这行，e2e 探针打印 `PASS` 后 **300 s 仍未退出**；加了之后 `[exit=0] 自行退出`）。
   仓库内回归钉子：`tools/dsh-remote/test/v2-desktop.test.mjs`
   「`v2/desktop：收到 turn/end 后订阅流被显式关闭（WS 句柄不泄漏）`」（D-06）。
